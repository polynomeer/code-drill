# 전체 기능 로드맵

> **역할**: 최초 기획의 전 범위 중 무엇이 서 있고, 남은 것을 어떤 순서로 짓는가
> **단일 출처**: 기능 단계의 순서와 그 순서를 정한 근거
> **갱신 트리거**: 한 단계를 닫았을 때, 또는 의존 관계가 바뀌었을 때

[production-readiness.md](production-readiness.md)는 **지금 있는 것을 팔 수 있는가**를 묻는다.
이 문서는 **원본 기획의 나머지를 어떤 순서로 지을 것인가**를 묻는다. 둘은 서로를 대체하지
않으며, 인프라 항목(A4·A5·B3)은 저쪽이 단일 출처다.

원본은 [specs/](specs/)의 `.docx` 다섯이며, 특히 기획서 부록 A의 기능 인벤토리(P0~P4)와
§14.2 단계별 로드맵이 이 문서의 상위 기준이다. 둘이 어긋나면 `.docx`가 이긴다.

## 1. 지금 어디에 서 있나

원본 로드맵(§14.2)은 여섯 단계다. 우리는 **단계 0을 끝내고 단계 1의 대부분**에 와 있다.
(이 절은 5단계를 닫은 시점 기준이다.)

| 원본 단계 | 핵심 산출물 | 상태 |
|---|---|---|
| 0. 기술·학습 검증 | 샌드박스, 이벤트 계측, 역량 증거 모델, 리플레이 | 닫힘 |
| 1. Competency Judge MVP | 저지·30문제·진단·코칭·변이·프로필 | **문제 수만 남음** (38/100) |
| 2~5 | 코칭 심화·콘텐츠·네트워크·수익화 | 시작 전 |

### P0 인벤토리 대비

기획서 부록 A의 P0 여덟 도메인이 출시의 바닥이다.

| 도메인 | 원본 요구 | 상태 |
|---|---|---|
| 계정 | 가입·로그인·프로필·설정 | 있음 (1단계) |
| 문제 | 검색·필터·상세·태그·난이도 | 있음 (1단계) |
| 에디터 | 언어·템플릿·자동저장·단축키 | 있음 |
| 실행 | 샘플·커스텀 테스트·diff | 있음 (2단계) |
| 채점 | 큐·컴파일·실행·그룹·부분점수 | 있음 |
| 제출 | 기록·코드·성능·diff | 있음 (2단계) |
| 관리 | 문제·테스트·런타임·재채점 | 있음 (2인 승인·감사 포함) |
| 시각화 | 배열·포인터·스택·큐·그래프 | 있음 (다섯 렌더러) |

**P0 여덟 도메인이 전부 섰다.** 1단계에서 계정과 문제를, 2단계에서 실행과 제출을 닫았다.

### 원본 MVP 정의(§14.1) 대비

| 포함하기로 한 것 | 상태 |
|---|---|
| 함수형 채점, 2~3개 언어 | 있음 (Kotlin·Java·Python) |
| 심층 문제 30~50개 | 38개 |
| 실행 리플레이 | 있음 |
| 변이 평가 | **저작 검증에만 있다.** 사용자 기능이 아니다 |
| 역량 태그·초기 진단 | 있음 (1·3단계) |
| 코칭 풀이 | 없음 |
| 복잡도 예측 | 있음 (2단계) |
| 커스텀 테스트 | 있음 (2단계) |
| 최초 분기점 | 없음 |
| 숙련도·신뢰도 | 있음 (3단계) |
| 일일 훈련·주간 리포트 | 없음 |

제품 정의 문장 — "역량을 분해해 진단하고, 약한 능력을 코칭하며, 새로운 문제로 전이를
검증한다" — 가 **네 조각 모두 섰다.** 남은 단계는 이 위에 얹히는 것들이다.

### 자리만 잡혀 있는 것

`coaching` 과 `learning` 모듈이 아직 **경계 주석만 있는 13줄짜리 빈 껍데기**다 (`competency`
는 3단계에서 채웠다). 소유 데이터와 금지 의존성이 이미 선언돼 있으므로 채워 넣을 자리는
정해져 있다.

## 2. 순서를 정하는 것은 우선순위가 아니라 의존성

부록 A의 P0~P4는 **가치의 순서**이지 **지을 수 있는 순서**가 아니다. P2로 적힌 최초
분기점이 P1 리플레이보다 뒤인 것은 맞지만, 그것을 지으려면 P1에 없는 참조 실행이 먼저
있어야 한다. 아래 셋이 위쪽 기능 대부분을 막고 있다.

**병목 1 — 문제에 메타데이터가 없다** — 풀렸다 (1단계).
`ProblemManifest` 에는 `id·title·statement·limits·signature·groups` 뿐이었다. 난이도도,
태그도, 역량도 없었다. 그래서 탐색(FR-201~203)이 막히고, **역량 태그가 없으니 어떤 증거도
어느 역량에 속하는지 말할 수 없었다.** 지금은 `catalog.yaml` 이 그 넷을 담는다.

**병목 2 — 증거의 원천이 제출 하나뿐이다** — 풀렸다 (2·3단계).
Competency 는 evidence 위에 선다. 원본이 세는 증거는 제출만이 아니라 **사전 질문 응답,
힌트 의존도, 사용자 테스트의 변이 탐지율, 반례 품질**이다(§8.2). 이제 사전 질문 응답과
커스텀 테스트가 쌓인다. 변이 탐지율과 힌트 의존도는 4단계에서 붙었다.

**병목 3 — 참조 실행이 없다.**
최초 분기점은 "사용자 코드와 참조 모델을 같은 최소 반례에서 실행"해 상태가 처음 갈라진
지점을 찾는다(§6.2). 지금 트레이스는 사용자 실행 하나만 남긴다. 참조 해답을 같은 계측으로
돌려 두 트레이스를 **정답 코드를 노출하지 않고** 비교하는 것이 전제다.

이 셋을 각각 1·2·3단계의 앞머리에 둔다.

## 3. 단계별 계획

각 단계는 원본 로드맵의 단계와 대응하되, **이미 서 있는 것만큼 줄였다.**

### 1단계. 문제를 찾을 수 있게, 역량을 붙일 수 있게 — 닫힘

> 원본 §14.2 단계 1의 남은 절반 중 탐색 부분. 병목 1을 풀었다.

- 난이도·태그·역량·선수 관계를 **`catalog.yaml`** 로 붙였다. 38문제 전부
- 목록 API·화면: 다중 필터(AND 로 겹치고 같은 종류 안에서 OR), 태그 후보와 건수,
  총 개수, 완료 상태, 정답률, URL 보존
- 계정 프로필·설정 화면 — 이름·비밀번호 변경, 데이터 반출, 계정 삭제

**manifest 가 아니라 옆 파일이다.** `packageDigest` 는 판정을 재현하는 근거이고, 이미
등록된 버전과 digest 가 다르면 등록이 거절된다 (§6.1). 난이도와 태그는 판정을 바꾸지
않으므로 manifest 에 넣으면 **오타 하나를 고치는 데도 문제 버전이 올라가고**, 버전 번호가
"무엇으로 채점됐는가"를 뜻하지 않게 된다. 경계는 한 문장이다 — **digest 에 드는 것은
판정을 바꾸는 것뿐이다.**

역량 온톨로지는 기획서 §4.2 의 다섯 역량군 열여섯 세부 역량을 그대로 옮겼다. 3단계부터
모든 증거가 이 위에 쌓이므로, 이름을 뒤에 바꾸면 지난 증거를 다시 해석해야 한다.

**하면서 드러난 것 둘.**

- 화면 두 곳이 각자 주소를 통째로 갈아 끼우고 있었다. 필터를 걸고 문제를 고르면 필터가
  사라졌다. 쿼리 문자열 주인을 한곳으로 모았다.
- 반출·삭제는 B1 에서 API 만 만들고 화면이 없었다. **화면 없는 개인정보 기능은 사용자에게
  없는 것과 같다.**

**남긴 것**: 정답률 정렬. 정렬 키를 늘리려면 커서에 그 키를 실어야 하는데, 값이 바뀌는
키로 페이지를 넘기면 항목이 건너뛰거나 겹친다. 목록이 길어져 정렬이 실제로 필요해질 때
투영 테이블과 함께 푼다.

### 2단계. 제출하지 않고도 코드를 시험할 수 있게 — 대부분 닫힘

> P0 '실행' 도메인. 병목 2의 절반을 풀었다.

- 커스텀 테스트: 한 줄에 한 케이스, 기대 출력은 선택. `ExecutionMode.TRIAL` 로 돈다
- 제출 상세: 코드 보기, 바로 이전 제출과의 줄 단위 diff, 판정·점수 변화
- 사전 질문: **알고리즘 선택·복잡도 예측** 두 가지. 응답은 근거·오개념과 함께 쌓인다

**판정과 나눈 곳이 셋이다.** 큐(시험 실행이 몰려도 채점이 뒤에 서지 않는다), 표(정답률과
역량 증거가 시험 실행을 세지 않는다), 오케스트레이터(임대와 fencing 은 판정이 두 번
기록되는 것을 막는 장치인데 여기에는 기록될 판정이 없다). 다만 Runner 는 **한 리스너로**
두 큐를 받는다 — 리스너까지 나누면 둘이 동시에 돌아 측정이 서로 오염된다 (§5.2).

**밟은 것.** "기대를 적지 않았다"를 자리값으로 흉내 내려다 두 번 막혔다. 처음에는 NUL
문자를 썼는데 jsonb 가 그것을 저장하지 못했고, 콜론 문자열로 바꿨더니 반환 타입 검사에
걸렸다. **어떤 자리값도 타입 검사를 통과해야 하고, 통과하는 순간 실제 출력과 우연히 같아질
수 있다.** `TestCase.expected` 를 nullable 로 만들어 "비교할 것이 없다"를 그대로 표현했다.

새 엔드포인트가 두 번 다 인증 경로 목록 밖이었다. 둘 다 열린 것이 아니라 닫힌 쪽으로
틀렸다 — 접두사로 거는 방식이 의도대로 동작했다.

**남긴 것 — 조건 추출 질문.** 알고리즘과 복잡도는 카탈로그가 정답을 갖고 있어 채점할 수
있지만, "이 문제가 보장하는 조건은 무엇인가"의 정답은 어디에도 없다. 지문의 제약을 구조화해
문제마다 적어야 하고, 그것은 38문제 저작 작업이다. 오개념 분류도 지금은 **답과 정답의
관계에서 나오는 것만** 한다 — 문제별 오개념("이분탐색 경계를 닫힌 구간으로 본다")은 사람이
적어야 하며, 적지 않은 채로 분류하는 척하면 3단계가 없는 신호를 읽는다.

### 3단계. 증거를 모아 숙련도로 바꾼다 — 닫힘

> `competency` 모듈을 채웠다. 원본 §14.2 단계 1의 나머지.

- 온톨로지 16개 세부 역량 위에 증거가 쌓인다. 원천 셋: **제출·사전 질문 응답·시험 실행**
- 등급(Level)·신뢰도(Confidence)·근거(Evidence)를 **합치지 않고** 따로 낸다
- 역량 지도: 근거를 펼치면 문제·시각·평가 방식·도움 수준이 나오고, 제출이면 그 제출을 연다

**숙련도를 저장하지 않는다.** 증거만 쌓고 물어볼 때 계산한다. 저장하면 계산 규칙을 고쳤을
때 옛 값이 새 규칙과 섞이고, "이 숫자가 어디서 나왔나"에 답하려면 결국 증거를 다시 봐야
한다. 저장소에 고치는 메서드를 두지 않은 것도 같은 이유다 — **원본 증거는 수정하지 않는다**
(§3.1의 금지 의존성).

**한 숫자로 합치지 않는 이유.** "72%" 는 세 번 풀어 두 번 맞힌 사람과 백 번 풀어 일흔두 번
맞힌 사람을 같게 보이게 하는데, 그 둘에게 필요한 다음 행동은 정반대다. 증거 둘로 얻은
`STRONG` 과 서른으로 얻은 `STRONG` 도 같은 등급이지만 같은 사실이 아니다.

**아직 재지 않은 역량을 감추지 않는다** (FR-801). 감추면 사용자는 자기가 무엇을 아직
보이지 않았는지 모른다. 0점으로 그리는 것은 더 나쁘다 — 모르는 것을 못한다고 말하는 셈이다.

**남긴 것.** 원본이 세는 증거 중 **힌트 의존도와 변이 탐지율**이 아직 없었다 — 둘 다
4단계에서 붙었다. 증거 무게 칸을 미리 만들어 둔 것이 그때 값을 했다: 도움 기능이 붙을 때
칸을 만들었다면 그 전 증거는 무게를 모르는 채로 남았을 것이다. 신뢰도는 표본 수로만 정하고 최근성은 넣지 않았다: "언제부터 오래된 것인가"를
정할 근거가 아직 없고, 근거 없는 규칙은 숫자를 그럴듯하게 만들 뿐이다 (6단계 복습 간격과
함께 붙인다).

### 4단계. 코칭과 전이 검증 — 닫힘

> `coaching` 모듈을 채웠다. 제품 정의 문장이 여기서 완성됐다.

- 한 세션에 약한 역량 1~2개만 개입, 도움 단계를 사용자가 확인 (FR-802)
- **변이 평가를 사용자 기능으로** (FR-804): 사용자 테스트를 변이 구현에 돌려 mutation
  score 와 누락 유형을 준다 — 숨은 정답 데이터는 노출하지 않는다
- 설명 과제와 변형 문제로 전이 확인 (FR-807). 힌트·AI 없이 완료한 결과가 가장 무거운 증거

**변이 평가는 방향을 뒤집은 것이다.** 저작 검증(§6.3)은 테스트를 고정해 두고 오답이
잡히는지 보고, 여기서는 오답을 고정해 두고 테스트가 잡는지 본다. 엔진은 같은 것을 쓴다 —
다르면 "저작 검증은 통과했는데 사용자 화면에서는 안 잡힌다"가 생긴다.

정답으로 사용자의 기대를 **먼저 검산한다.** 기대 출력이 실제 정답과 다르면 그 케이스는
시험이 아니라 틀린 시험이고, 그것으로 오답을 "잡았다"고 세면 점수가 거짓이 된다 — 틀린
기대는 정답도 오답도 똑같이 떨어뜨리기 때문이다. 성능 오답은 점수에서 뺀다: 잡으려면
한도를 넘길 만큼 큰 입력이 필요한데 테스트 패널에 손으로 적을 수 있는 것이 아니라,
빼지 않으면 아무도 100% 를 받을 수 없고 그 감점은 사용자가 고칠 수 없는 것에 대한 감점이다.

**힌트는 문제가 이미 갖고 있는 것에서 만든다.** 목표 복잡도는 `catalog.yaml` 에,
"여기서 흔히 무너진다"는 `mutants/` 의 설명 줄에 이미 있다. 산문이 필요한 자리
(모델링·구현력·문제 독해)에만 `hints.yaml` 을 썼다 — 30개 문제, 역량마다 두 단계.
같은 사실을 두 곳에 쓰면 오답을 고쳤을 때 힌트만 옛말이 된다.

**밀지 않고 당긴다.** 세션도 단계도 사용자가 누른다. 사다리 본문은 펼칠 때만 응답에
실린다 — 통째로 내려보내고 화면에서 가리면 개발자 도구를 열 줄 아는 사람에게는 도움이
아니라 정답이고, 그 사람의 증거만 조용히 부풀려진다.

**전이는 다른 문제에서만 드러난다.** 변형 문제는 저작자가 **선수로 적어 둔 관계**를 먼저
본다. 겹치는 역량만으로 고르다가 두 수의 합에서 이분 그래프 판정이 나왔다 — 둘 다 모델링과
구현력을 요구하는 것은 맞지만, 해시맵으로 짝을 찾던 생각이 그래프 색칠로 옮겨 갈 리는 없다.
역량 태그는 **무엇을 재는지**를 말할 뿐 **무엇이 이어지는지**는 말해 주지 않는다.

**증거 무게가 처음으로 1.0 을 벗어난다.** 힌트 1·2·3단계가 0.7·0.45·0.3 이고, 확인된
전이가 1.5 다. 0 으로 내리지 않는 이유는 도움을 받고 푼 것도 못 푼 것보다는 아는 것이며,
0 이면 사용자가 막혀도 힌트를 누르지 않아 코칭이 있으나 마나가 되기 때문이다. 세션을 닫아도
도움은 세어진다 — 3단계까지 보고 닫은 뒤 제출하면 무게가 온전해지는 구멍을 두면, 그 구멍을
아는 사람의 숙련도만 높아진다.

**남긴 것.** 설명 과제의 글은 아직 증거가 되지 않는다. 채점할 방법이 없어 무엇을 써도
"썼다" 밖에 말할 수 없고, 그것으로 설명 역량을 올리면 지도가 거짓말을 한다. 저장하고
되돌려 보여 주되 역량은 움직이지 않으며, 글을 채점하는 것은 10단계 AI 모드다.

**통과 기준**: 코칭 세션 후 힌트 없는 변형 문제 성과가 개선된다 — 원본이 MVP 성공 조건으로
적어 둔 바로 그 문장(§14.1)이다. **이제 그것을 잴 수 있다** (`transfer_task.status`). 값은
사용자가 쌓여야 나온다.

### 5단계. 최초 분기점과 최소 반례 — 닫힘

> 병목 3을 풀었다. 원본 §14.2 단계 2.

- 참조 해답을 같은 계측으로 실행해 트레이스를 남긴다
- 상태 계약 기반 비교: **참조 코드를 노출하지 않고** 최초로 갈라진 이벤트만 공개
- 최소 반례 자동 축소: delta debugging (§6.3)
- 리플레이 중 다음 상태 예측 (FR-805)

**상태 계약은 (종류, 대상, 결과) 셋이다.** seq 도 코드 줄도 비교에 넣지 않는다 — 계측
호출을 한 줄 옮겼다고 갈라진 것이 아니고, 그것으로 비교하면 코드를 정리한 사람이 벌을
받는다. 반대로 대상이 다르면 값이 같아도 갈라진 것이다: 3번을 봐야 할 자리에서 4번을
본 것은 우연히 답이 같아도 다른 일을 한 것이다.

**첫 이벤트부터 다르면 갈라진 것이 아니라 다른 길이다.** 그때는 지점을 짚지 않고 그
사실만 말하며, 참조가 무엇을 했는지도 말하지 않는다 — 참조의 한 걸음을 내보내는 유일한
명분은 "같이 오다가 여기서 갈렸다"를 설명하는 것인데, 함께 온 길이 없으면 남는 것은
공짜로 새는 첫 수뿐이다.

**참조 지문에 이벤트 본문을 담지 않는다.** 담는 것은 정규화 키뿐이라, 저장소가 물리적으로
분기 한 줄보다 더 내놓을 수 없다. 지문은 (문제 버전, 케이스) 의 함수라 한 번만 계산한다.

**축소의 전제 조건 검사기는 참조 풀이다.** 원소를 지우다 보면 "정답은 항상 정확히 하나
존재한다" 같은 전제를 깨뜨린 입력이 나오는데, 그런 입력에서는 참조도 터진다. 그것을
후보에서 떨어뜨리면 **문제별 shrinker 를 쓰지 않고도** 유효한 입력만 남는다 — 무엇이
유효한 입력인지 이미 아는 코드가 저장소에 있는데 그 지식을 다시 쓸 이유가 없다. 로드맵이
`문제별 shrinker` 를 함께 적어 두었는데, 그것 없이 서는 길이 있었다.

**어느 케이스가 떨어졌는지 제어 영역은 모른다.** 숨은 그룹의 케이스 내역은 판정 봉투에서
잘려 나가고(§8.3), 떨어지는 것은 대개 그 숨은 그룹이다. 그래서 후보를 전부 보내고 어느
것이 재현되는지는 실제로 돌려 보는 쪽이 정한다.

**계측 이벤트가 코드 줄을 달고 나온다.** 이것이 없어 화면이 이벤트를 코드에 이을 방법이
아예 없었다 — 조용한 실패였다. 트레이스는 멀쩡히 나오고 코드 강조만 안 될 뿐이라
드러나지 않는다. 세 언어 모두 호출자의 프레임에서 읽으며, 계측 실행에서만 돈다.

**예측 증거의 무게는 0.5 다.** 트레이스는 이미 화면에 있어 마음먹으면 답을 보고 누를 수
있고, 그 구멍은 막을 수 없다 — 자기 실행의 기록을 자기에게 숨길 수는 없다. 감출 수 없는
구멍이면 감추는 척하는 대신 값을 낮춰 세는 것이 맞다.

**남긴 것.** 반례 축소는 **배열 인자만** 줄인다. 정수 인자를 임의로 줄이면 전제가 깨진
입력만 나오고 참조가 전부 떨어뜨리므로, 값을 줄이려면 문제별 지식이 필요하다 — 8단계
콘텐츠와 함께 붙일 자리다. 큰 입력에서만 재현되는 결함도 놓친다: 시작 후보에 원소 예산을
두었기 때문이며, 그런 결함은 대개 값이 아니라 시간·메모리 쪽이라 축소가 답할 문제가 아니다.

**통과 기준**: 선택·근거·결과가 코드·입력·이벤트 시점과 연결된다. 정답 데이터가 API 로
새지 않는다.

### 6단계. 학습 루프

> `learning` 모듈을 채운다. 원본 §14.2 단계 2의 나머지.

- 문제집, 학습 계획, 오늘의 문제, 유연한 회복 규칙의 스트릭
- 일일 처방과 주간 리포트: 추천 이유와 다음 측정 시점 (FR-808)
- 통계: 정답률·주제별·실수 유형
- 추천은 정답률이 아니라 **최근 오답 원인·힌트 의존도·복습 간격·전이 성과**로 (§8.1)

**통과 기준**: 추천마다 이유가 붙고 사용자가 조정할 수 있다.

### 7단계. 해설·비교·실험실

> 원본 §6.4~6.6. 리플레이 위에 얹힌다.

- 인터랙티브 해설: 입력을 바꾸면 해설과 시각화가 다시 실행된다
- 풀이 비교 경기장: 방문 순서·연산량·메모리·중복 계산·최악 입력·최초 선택 차이 (§6.5)
- 알고리즘 실험실: 입력 직접 편집, 여러 알고리즘 동시 실행, 사용자 함수 교체

**주의**: 비교와 실험실은 **실행 횟수를 곱한다.** 쿼터와 비용 모델을 함께 설계하지 않으면
여기서 단위 경제성이 깨진다 (§15 비용 구조).

### 8단계. 콘텐츠 규모

> 원본 §14.2 단계 3. **다른 단계와 병렬로 계속 돈다.**

- 핵심 100문제 (§10.1). 지금 38개
- 문제당 산출물: 서브태스크, 복수 접근, 인터랙티브 해설, 대표 오답, 최소 반례, 풀이 비교,
  후속 문제, 반례 미션
- 검수 워크플로: 초안 → 기술 → 데이터 → 시각화 → 공개 (§5.5)

**이미 서 있는 것**: 저작 도구, 검증 파이프라인 일곱 검사, 2인 승인, 재채점. 원본이
"제작 비용이 지속 불가능하면 문제 수보다 제작 도구에 투자한다"고 적어 둔 그 도구가 이미 있다.

**이것은 사람 시간이다.** 앞 단계들이 문제당 산출물을 늘리므로, **1·5단계 뒤에 본격화하는
편이 재작업이 적다.**

### 9단계. 네트워크

> 원본 §14.2 단계 4.

- 대회: 정기 레이팅, 비레이팅, 가상 참가, 미니 대결, 반례 대전 (§8.4)
- 반례 아레나: 익명 오답 깨뜨리기, 자동 축소, 가정 분류, 검수 (§8.3)
- 커뮤니티: 질문 게시판, 풀이, 리플레이 시점 주석, 기여자 평판 (§8.5)

**전제**: 반례 아레나는 5단계의 축소기가, 대회는 §11.4 부정행위 방어가 먼저 있어야 한다.

### 10단계. AI 협업 모드

> 원본 §7 전체. **원본이 스스로 게이트를 걸어 둔 단계다.**

§15.1: "기본 저지의 안정성과 속도가 목표에 도달하기 전에는 대규모 AI 기능 개발을 시작하지
않는다."

- 페어 프로그래밍 일곱 역할 (§7.1)
- Plan → Delegate → Verify (§7.2), AI 협업 리플레이 (§7.3)
- 검증 중심 챌린지 여섯 (§7.4), 제한 예산 에이전트 (§7.5)
- 최종 소유권 확인 (§7.6), 적대적 AI·보안 모드 (§7.7)

### 11단계. 교육기관·기업

> 원본 §9, §14.2 단계 5.

- 교육기관: 비공개 그룹, 과제·마감, 학급 전체의 최초 분기점 분포, 시험 중 기능 제한
- 기업 평가: 평가 템플릿, AI 모드 구성, 과정 기록 제공, 면접에서 리플레이 재생
- 장기 실무형: 레거시 고고학, 변경 영향 예측, 요구사항 정합성, 장애 대응, AI PR 승인, 사양 저지

**원본의 경고**(§15.1): "B2B 요구가 소비자 학습 경험을 훼손하면 실행 인프라는 공유하되
제품 표면을 분리한다."

## 4. 인프라는 어디에 끼는가

[production-readiness.md](production-readiness.md)에 남은 A4(워크로드 신원)·A5(컴파일
격리)·B3(오브젝트 스토어)는 **기능이 아니라 규모의 전제**다. 끼는 자리는 이렇다.

| 무엇이 그것을 요구하나 | 항목 |
|---|---|
| 2단계 커스텀 테스트 — 실행량이 몇 배로 는다 | A5 컴파일 격리 |
| 7단계 비교·실험실 — 다시 몇 배 | A5, 노드 여럿 → A4 |
| 8단계 콘텐츠 100문제 — 소스와 트레이스 저장량 | B3 오브젝트 스토어 |

**2단계 전에 배포 대상을 정해야 한다.** 그 결정 하나가 A4·A5·B3 와 3배 여유 재측정을
한꺼번에 연다.

## 5. 비용이 특별히 큰 것

| 항목 | 왜 비싼가 |
|---|---|
| 역량 온톨로지 설계 (3단계) | 한 번 정하면 모든 증거가 그 위에 쌓인다. 뒤에 바꾸면 지난 증거를 다시 해석해야 한다 |
| 핵심 100문제 (8단계) | 원본이 §15 에서 첫 번째 리스크로 꼽은 것. 문제당 산출물이 여덟 가지다 |
| 참조 실행 비교 (5단계) | 정답 노출 없이 상태만 비교해야 한다. 계약 설계가 구현보다 어렵다 |
| AI 모드 (10단계) | 원본 스스로 게이트를 걸었다. 저지가 안정되기 전에는 시작하지 않는다 |

## 6. 다음 한 걸음

**6단계 — 학습 루프.**

병목 셋이 모두 풀렸다. 문제 메타데이터(1단계), 증거의 원천(2·3단계), 참조 실행(5단계)이
서 있으므로, 남은 단계는 전부 이 위에 얹히는 것들이다.

6단계가 3단계에 남긴 숙제를 하나 가져간다. **신뢰도가 표본 수로만 정해져 있다** — 최근성을
넣지 않은 것은 "언제부터 오래된 것인가"를 정할 근거가 없어서였고, 복습 간격이 실제로
정해지면 그 근거가 생긴다.

콘텐츠 쪽에서는 **문제 수가 유일한 남은 MVP 항목**이다 (38/100, 8단계). 반례 축소의
정수 인자 shrinker 도 그때 함께 붙일 자리다.

인프라 쪽에서는 단일 호스트까지 섰다. 다음은 **다중 노드**이며, A4(워크로드 신원)와
A5(컴파일 격리)가 거기서 함께 풀린다 ([production-readiness.md](production-readiness.md)).
