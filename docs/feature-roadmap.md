# 전체 기능 로드맵

> **역할**: 최초 기획의 전 범위 중 무엇이 서 있고, 남은 것을 어떤 순서로 짓는가
> **단일 출처**: 기능 단계의 순서와 그 순서를 정한 근거
> **갱신 트리거**: 한 단계를 닫았을 때, 또는 의존 관계가 바뀌었을 때

[production-readiness.md](production-readiness.md)는 **지금 있는 것을 팔 수 있는가**를 묻는다.
이 문서는 **원본 기획의 나머지를 어떤 순서로 지을 것인가**를 묻는다. 둘은 서로를 대체하지
않으며, 인프라 항목(A4·A5·B3)은 저쪽이 단일 출처다.

원본은 [specs/](specs/)의 `.docx` 다섯이며, 특히 기획서 부록 A의 기능 인벤토리(P0~P4)와
§14.2 단계별 로드맵이 이 문서의 상위 기준이다. 둘이 어긋나면 `.docx`가 이긴다.

## 1. 지금 어디에 서 있나

원본 로드맵(§14.2)은 여섯 단계다. 우리는 **단계 0을 끝내고 단계 1의 대부분**에 와 있다.
(이 절은 9단계의 아레나를 연 시점 기준이다.)

| 원본 단계 | 핵심 산출물 | 상태 |
|---|---|---|
| 0. 기술·학습 검증 | 샌드박스, 이벤트 계측, 역량 증거 모델, 리플레이 | 닫힘 |
| 1. Competency Judge MVP | 저지·30문제·진단·코칭·변이·프로필 | 닫힘 (166문제, 원본 기준 30~50) |
| 2~5 | 코칭 심화·콘텐츠·네트워크·수익화 | 시작 전 |

### P0 인벤토리 대비

기획서 부록 A의 P0 여덟 도메인이 출시의 바닥이다.

| 도메인 | 원본 요구 | 상태 |
|---|---|---|
| 계정 | 가입·로그인·프로필·설정 | 있음 (1단계) |
| 문제 | 검색·필터·상세·태그·난이도 | 있음 (1단계) |
| 에디터 | 언어·템플릿·자동저장·단축키 | 있음 |
| 실행 | 샘플·커스텀 테스트·diff | 있음 (2단계) |
| 채점 | 큐·컴파일·실행·그룹·부분점수 | 있음 |
| 제출 | 기록·코드·성능·diff | 있음 (2단계) |
| 관리 | 문제·테스트·런타임·재채점 | 있음 (2인 승인·감사 포함) |
| 시각화 | 배열·포인터·스택·큐·그래프 | 있음 (다섯 렌더러) |

**P0 여덟 도메인이 전부 섰다.** 1단계에서 계정과 문제를, 2단계에서 실행과 제출을 닫았다.

### 원본 MVP 정의(§14.1) 대비

| 포함하기로 한 것 | 상태 |
|---|---|
| 함수형 채점, 2~3개 언어 | 있음 (Kotlin·Java·Python) |
| 심층 문제 30~50개 | 52개 |
| 실행 리플레이 | 있음 |
| 변이 평가 | **저작 검증에만 있다.** 사용자 기능이 아니다 |
| 역량 태그·초기 진단 | 있음 (1·3단계) |
| 코칭 풀이 | 없음 |
| 복잡도 예측 | 있음 (2단계) |
| 커스텀 테스트 | 있음 (2단계) |
| 최초 분기점 | 없음 |
| 숙련도·신뢰도 | 있음 (3단계) |
| 일일 훈련·주간 리포트 | 없음 |

제품 정의 문장 — "역량을 분해해 진단하고, 약한 능력을 코칭하며, 새로운 문제로 전이를
검증한다" — 가 **네 조각 모두 섰다.** 남은 단계는 이 위에 얹히는 것들이다.

### 자리만 잡혀 있는 것

`coaching` 과 `learning` 모듈이 아직 **경계 주석만 있는 13줄짜리 빈 껍데기**다 (`competency`
는 3단계에서 채웠다). 소유 데이터와 금지 의존성이 이미 선언돼 있으므로 채워 넣을 자리는
정해져 있다.

## 2. 순서를 정하는 것은 우선순위가 아니라 의존성

부록 A의 P0~P4는 **가치의 순서**이지 **지을 수 있는 순서**가 아니다. P2로 적힌 최초
분기점이 P1 리플레이보다 뒤인 것은 맞지만, 그것을 지으려면 P1에 없는 참조 실행이 먼저
있어야 한다. 아래 셋이 위쪽 기능 대부분을 막고 있다.

**병목 1 — 문제에 메타데이터가 없다** — 풀렸다 (1단계).
`ProblemManifest` 에는 `id·title·statement·limits·signature·groups` 뿐이었다. 난이도도,
태그도, 역량도 없었다. 그래서 탐색(FR-201~203)이 막히고, **역량 태그가 없으니 어떤 증거도
어느 역량에 속하는지 말할 수 없었다.** 지금은 `catalog.yaml` 이 그 넷을 담는다.

**병목 2 — 증거의 원천이 제출 하나뿐이다** — 풀렸다 (2·3단계).
Competency 는 evidence 위에 선다. 원본이 세는 증거는 제출만이 아니라 **사전 질문 응답,
힌트 의존도, 사용자 테스트의 변이 탐지율, 반례 품질**이다(§8.2). 이제 사전 질문 응답과
커스텀 테스트가 쌓인다. 변이 탐지율과 힌트 의존도는 4단계에서 붙었다.

**병목 3 — 참조 실행이 없다** — 풀렸다 (5단계).
최초 분기점은 "사용자 코드와 참조 모델을 같은 최소 반례에서 실행"해 상태가 처음 갈라진
지점을 찾는다. 참조 해답을 같은 계측으로 돌린 **지문**을 (문제 버전, 케이스) 마다 한 번
계산해 두고, 사용자 트레이스와 견줘 처음 갈라진 자리만 낸다. 지문에는 이벤트 본문을 담지
않아 저장소가 물리적으로 그 한 줄보다 더 내놓을 수 없다.

이 셋을 각각 1·2·3단계의 앞머리에 두었고, 셋 다 닫혔다.

## 3. 단계별 계획

각 단계는 원본 로드맵의 단계와 대응하되, **이미 서 있는 것만큼 줄였다.**

### 1단계. 문제를 찾을 수 있게, 역량을 붙일 수 있게 — 닫힘

> 원본 §14.2 단계 1의 남은 절반 중 탐색 부분. 병목 1을 풀었다.

- 난이도·태그·역량·선수 관계를 **`catalog.yaml`** 로 붙였다. 38문제 전부
- 목록 API·화면: 다중 필터(AND 로 겹치고 같은 종류 안에서 OR), 태그 후보와 건수,
  총 개수, 완료 상태, 정답률, URL 보존
- 계정 프로필·설정 화면 — 이름·비밀번호 변경, 데이터 반출, 계정 삭제

**manifest 가 아니라 옆 파일이다.** `packageDigest` 는 판정을 재현하는 근거이고, 이미
등록된 버전과 digest 가 다르면 등록이 거절된다 (§6.1). 난이도와 태그는 판정을 바꾸지
않으므로 manifest 에 넣으면 **오타 하나를 고치는 데도 문제 버전이 올라가고**, 버전 번호가
"무엇으로 채점됐는가"를 뜻하지 않게 된다. 경계는 한 문장이다 — **digest 에 드는 것은
판정을 바꾸는 것뿐이다.**

역량 온톨로지는 기획서 §4.2 의 다섯 역량군 열여섯 세부 역량을 그대로 옮겼다. 3단계부터
모든 증거가 이 위에 쌓이므로, 이름을 뒤에 바꾸면 지난 증거를 다시 해석해야 한다.

**하면서 드러난 것 둘.**

- 화면 두 곳이 각자 주소를 통째로 갈아 끼우고 있었다. 필터를 걸고 문제를 고르면 필터가
  사라졌다. 쿼리 문자열 주인을 한곳으로 모았다.
- 반출·삭제는 B1 에서 API 만 만들고 화면이 없었다. **화면 없는 개인정보 기능은 사용자에게
  없는 것과 같다.**

**남긴 것**: 정답률 정렬. 정렬 키를 늘리려면 커서에 그 키를 실어야 하는데, 값이 바뀌는
키로 페이지를 넘기면 항목이 건너뛰거나 겹친다. 목록이 길어져 정렬이 실제로 필요해질 때
투영 테이블과 함께 푼다.

### 2단계. 제출하지 않고도 코드를 시험할 수 있게 — 대부분 닫힘

> P0 '실행' 도메인. 병목 2의 절반을 풀었다.

- 커스텀 테스트: 한 줄에 한 케이스, 기대 출력은 선택. `ExecutionMode.TRIAL` 로 돈다
- 제출 상세: 코드 보기, 바로 이전 제출과의 줄 단위 diff, 판정·점수 변화
- 사전 질문: **알고리즘 선택·복잡도 예측** 두 가지. 응답은 근거·오개념과 함께 쌓인다

**판정과 나눈 곳이 셋이다.** 큐(시험 실행이 몰려도 채점이 뒤에 서지 않는다), 표(정답률과
역량 증거가 시험 실행을 세지 않는다), 오케스트레이터(임대와 fencing 은 판정이 두 번
기록되는 것을 막는 장치인데 여기에는 기록될 판정이 없다). 다만 Runner 는 **한 리스너로**
두 큐를 받는다 — 리스너까지 나누면 둘이 동시에 돌아 측정이 서로 오염된다 (§5.2).

**밟은 것.** "기대를 적지 않았다"를 자리값으로 흉내 내려다 두 번 막혔다. 처음에는 NUL
문자를 썼는데 jsonb 가 그것을 저장하지 못했고, 콜론 문자열로 바꿨더니 반환 타입 검사에
걸렸다. **어떤 자리값도 타입 검사를 통과해야 하고, 통과하는 순간 실제 출력과 우연히 같아질
수 있다.** `TestCase.expected` 를 nullable 로 만들어 "비교할 것이 없다"를 그대로 표현했다.

새 엔드포인트가 두 번 다 인증 경로 목록 밖이었다. 둘 다 열린 것이 아니라 닫힌 쪽으로
틀렸다 — 접두사로 거는 방식이 의도대로 동작했다.

**남긴 것 — 조건 추출 질문.** 알고리즘과 복잡도는 카탈로그가 정답을 갖고 있어 채점할 수
있지만, "이 문제가 보장하는 조건은 무엇인가"의 정답은 어디에도 없다. 지문의 제약을 구조화해
문제마다 적어야 하고, 그것은 38문제 저작 작업이다. 오개념 분류도 지금은 **답과 정답의
관계에서 나오는 것만** 한다 — 문제별 오개념("이분탐색 경계를 닫힌 구간으로 본다")은 사람이
적어야 하며, 적지 않은 채로 분류하는 척하면 3단계가 없는 신호를 읽는다.

### 3단계. 증거를 모아 숙련도로 바꾼다 — 닫힘

> `competency` 모듈을 채웠다. 원본 §14.2 단계 1의 나머지.

- 온톨로지 16개 세부 역량 위에 증거가 쌓인다. 원천 셋: **제출·사전 질문 응답·시험 실행**
- 등급(Level)·신뢰도(Confidence)·근거(Evidence)를 **합치지 않고** 따로 낸다
- 역량 지도: 근거를 펼치면 문제·시각·평가 방식·도움 수준이 나오고, 제출이면 그 제출을 연다

**숙련도를 저장하지 않는다.** 증거만 쌓고 물어볼 때 계산한다. 저장하면 계산 규칙을 고쳤을
때 옛 값이 새 규칙과 섞이고, "이 숫자가 어디서 나왔나"에 답하려면 결국 증거를 다시 봐야
한다. 저장소에 고치는 메서드를 두지 않은 것도 같은 이유다 — **원본 증거는 수정하지 않는다**
(§3.1의 금지 의존성).

**한 숫자로 합치지 않는 이유.** "72%" 는 세 번 풀어 두 번 맞힌 사람과 백 번 풀어 일흔두 번
맞힌 사람을 같게 보이게 하는데, 그 둘에게 필요한 다음 행동은 정반대다. 증거 둘로 얻은
`STRONG` 과 서른으로 얻은 `STRONG` 도 같은 등급이지만 같은 사실이 아니다.

**아직 재지 않은 역량을 감추지 않는다** (FR-801). 감추면 사용자는 자기가 무엇을 아직
보이지 않았는지 모른다. 0점으로 그리는 것은 더 나쁘다 — 모르는 것을 못한다고 말하는 셈이다.

**남긴 것.** 원본이 세는 증거 중 **힌트 의존도와 변이 탐지율**이 아직 없었다 — 둘 다
4단계에서 붙었다. 증거 무게 칸을 미리 만들어 둔 것이 그때 값을 했다: 도움 기능이 붙을 때
칸을 만들었다면 그 전 증거는 무게를 모르는 채로 남았을 것이다. 신뢰도는 표본 수로만 정하고 최근성은 넣지 않았다: "언제부터 오래된 것인가"를
정할 근거가 아직 없고, 근거 없는 규칙은 숫자를 그럴듯하게 만들 뿐이다 (6단계 복습 간격과
함께 붙인다).

### 4단계. 코칭과 전이 검증 — 닫힘

> `coaching` 모듈을 채웠다. 제품 정의 문장이 여기서 완성됐다.

- 한 세션에 약한 역량 1~2개만 개입, 도움 단계를 사용자가 확인 (FR-802)
- **변이 평가를 사용자 기능으로** (FR-804): 사용자 테스트를 변이 구현에 돌려 mutation
  score 와 누락 유형을 준다 — 숨은 정답 데이터는 노출하지 않는다
- 설명 과제와 변형 문제로 전이 확인 (FR-807). 힌트·AI 없이 완료한 결과가 가장 무거운 증거

**변이 평가는 방향을 뒤집은 것이다.** 저작 검증(§6.3)은 테스트를 고정해 두고 오답이
잡히는지 보고, 여기서는 오답을 고정해 두고 테스트가 잡는지 본다. 엔진은 같은 것을 쓴다 —
다르면 "저작 검증은 통과했는데 사용자 화면에서는 안 잡힌다"가 생긴다.

정답으로 사용자의 기대를 **먼저 검산한다.** 기대 출력이 실제 정답과 다르면 그 케이스는
시험이 아니라 틀린 시험이고, 그것으로 오답을 "잡았다"고 세면 점수가 거짓이 된다 — 틀린
기대는 정답도 오답도 똑같이 떨어뜨리기 때문이다. 성능 오답은 점수에서 뺀다: 잡으려면
한도를 넘길 만큼 큰 입력이 필요한데 테스트 패널에 손으로 적을 수 있는 것이 아니라,
빼지 않으면 아무도 100% 를 받을 수 없고 그 감점은 사용자가 고칠 수 없는 것에 대한 감점이다.

**힌트는 문제가 이미 갖고 있는 것에서 만든다.** 목표 복잡도는 `catalog.yaml` 에,
"여기서 흔히 무너진다"는 `mutants/` 의 설명 줄에 이미 있다. 산문이 필요한 자리
(모델링·구현력·문제 독해)에만 `hints.yaml` 을 썼다 — 30개 문제, 역량마다 두 단계.
같은 사실을 두 곳에 쓰면 오답을 고쳤을 때 힌트만 옛말이 된다.

**밀지 않고 당긴다.** 세션도 단계도 사용자가 누른다. 사다리 본문은 펼칠 때만 응답에
실린다 — 통째로 내려보내고 화면에서 가리면 개발자 도구를 열 줄 아는 사람에게는 도움이
아니라 정답이고, 그 사람의 증거만 조용히 부풀려진다.

**전이는 다른 문제에서만 드러난다.** 변형 문제는 저작자가 **선수로 적어 둔 관계**를 먼저
본다. 겹치는 역량만으로 고르다가 두 수의 합에서 이분 그래프 판정이 나왔다 — 둘 다 모델링과
구현력을 요구하는 것은 맞지만, 해시맵으로 짝을 찾던 생각이 그래프 색칠로 옮겨 갈 리는 없다.
역량 태그는 **무엇을 재는지**를 말할 뿐 **무엇이 이어지는지**는 말해 주지 않는다.

**증거 무게가 처음으로 1.0 을 벗어난다.** 힌트 1·2·3단계가 0.7·0.45·0.3 이고, 확인된
전이가 1.5 다. 0 으로 내리지 않는 이유는 도움을 받고 푼 것도 못 푼 것보다는 아는 것이며,
0 이면 사용자가 막혀도 힌트를 누르지 않아 코칭이 있으나 마나가 되기 때문이다. 세션을 닫아도
도움은 세어진다 — 3단계까지 보고 닫은 뒤 제출하면 무게가 온전해지는 구멍을 두면, 그 구멍을
아는 사람의 숙련도만 높아진다.

**남긴 것.** 설명 과제의 글은 아직 증거가 되지 않는다. 채점할 방법이 없어 무엇을 써도
"썼다" 밖에 말할 수 없고, 그것으로 설명 역량을 올리면 지도가 거짓말을 한다. 저장하고
되돌려 보여 주되 역량은 움직이지 않으며, 글을 채점하는 것은 10단계 AI 모드다.

**통과 기준**: 코칭 세션 후 힌트 없는 변형 문제 성과가 개선된다 — 원본이 MVP 성공 조건으로
적어 둔 바로 그 문장(§14.1)이다. **이제 그것을 잴 수 있다** (`transfer_task.status`). 값은
사용자가 쌓여야 나온다.

### 5단계. 최초 분기점과 최소 반례 — 닫힘

> 병목 3을 풀었다. 원본 §14.2 단계 2.

- 참조 해답을 같은 계측으로 실행해 트레이스를 남긴다
- 상태 계약 기반 비교: **참조 코드를 노출하지 않고** 최초로 갈라진 이벤트만 공개
- 최소 반례 자동 축소: delta debugging (§6.3)
- 리플레이 중 다음 상태 예측 (FR-805)

**상태 계약은 (종류, 대상, 결과) 셋이다.** seq 도 코드 줄도 비교에 넣지 않는다 — 계측
호출을 한 줄 옮겼다고 갈라진 것이 아니고, 그것으로 비교하면 코드를 정리한 사람이 벌을
받는다. 반대로 대상이 다르면 값이 같아도 갈라진 것이다: 3번을 봐야 할 자리에서 4번을
본 것은 우연히 답이 같아도 다른 일을 한 것이다.

**첫 이벤트부터 다르면 갈라진 것이 아니라 다른 길이다.** 그때는 지점을 짚지 않고 그
사실만 말하며, 참조가 무엇을 했는지도 말하지 않는다 — 참조의 한 걸음을 내보내는 유일한
명분은 "같이 오다가 여기서 갈렸다"를 설명하는 것인데, 함께 온 길이 없으면 남는 것은
공짜로 새는 첫 수뿐이다.

**참조 지문에 이벤트 본문을 담지 않는다.** 담는 것은 정규화 키뿐이라, 저장소가 물리적으로
분기 한 줄보다 더 내놓을 수 없다. 지문은 (문제 버전, 케이스) 의 함수라 한 번만 계산한다.

**축소의 전제 조건 검사기는 참조 풀이다.** 원소를 지우다 보면 "정답은 항상 정확히 하나
존재한다" 같은 전제를 깨뜨린 입력이 나오는데, 그런 입력에서는 참조도 터진다. 그것을
후보에서 떨어뜨리면 **문제별 shrinker 를 쓰지 않고도** 유효한 입력만 남는다 — 무엇이
유효한 입력인지 이미 아는 코드가 저장소에 있는데 그 지식을 다시 쓸 이유가 없다. 로드맵이
`문제별 shrinker` 를 함께 적어 두었는데, 그것 없이 서는 길이 있었다.

**어느 케이스가 떨어졌는지 제어 영역은 모른다.** 숨은 그룹의 케이스 내역은 판정 봉투에서
잘려 나가고(§8.3), 떨어지는 것은 대개 그 숨은 그룹이다. 그래서 후보를 전부 보내고 어느
것이 재현되는지는 실제로 돌려 보는 쪽이 정한다.

**계측 이벤트가 코드 줄을 달고 나온다.** 이것이 없어 화면이 이벤트를 코드에 이을 방법이
아예 없었다 — 조용한 실패였다. 트레이스는 멀쩡히 나오고 코드 강조만 안 될 뿐이라
드러나지 않는다. 세 언어 모두 호출자의 프레임에서 읽으며, 계측 실행에서만 돈다.

**예측 증거의 무게는 0.5 다.** 트레이스는 이미 화면에 있어 마음먹으면 답을 보고 누를 수
있고, 그 구멍은 막을 수 없다 — 자기 실행의 기록을 자기에게 숨길 수는 없다. 감출 수 없는
구멍이면 감추는 척하는 대신 값을 낮춰 세는 것이 맞다.

**남긴 것.** 반례 축소는 **배열 인자만** 줄인다. 정수 인자를 임의로 줄이면 전제가 깨진
입력만 나오고 참조가 전부 떨어뜨리므로, 값을 줄이려면 문제별 지식이 필요하다 — 8단계
콘텐츠와 함께 붙일 자리다. 큰 입력에서만 재현되는 결함도 놓친다: 시작 후보에 원소 예산을
두었기 때문이며, 그런 결함은 대개 값이 아니라 시간·메모리 쪽이라 축소가 답할 문제가 아니다.

**통과 기준**: 선택·근거·결과가 코드·입력·이벤트 시점과 연결된다. 정답 데이터가 API 로
새지 않는다.

### 6단계. 학습 루프 — 닫힘

> `learning` 모듈을 채웠다. 원본 §14.2 단계 2의 나머지.

- 오늘의 처방: 이유·다음 측정 시점이 붙은 문제 최대 셋, 밀어내기 (FR-808)
- 주간 리포트: 약점·재발·성장·다음 행동 (FR-808)
- 문제집 (FR-205), 통계 (정답률·주제별·판정 분포), 유연한 회복 규칙의 스트릭
- 추천은 정답률이 아니라 **최근 오답 원인·힌트 의존도·복습 간격·전이 성과**로 (§8.1)

**정답률은 어디에도 없다.** 기획서가 넣으라고 한 넷이 순서대로 이유가 되고, 그 뒤에 약점
보완과 선수 관계의 다음 단계가 온다. 정답률이 높은 문제를 권하면 쉬운 것만 돌게 되고 낮은
문제를 권하면 어려운 것에 부딪히기만 하며, 둘 다 "이 사람에게 지금 무엇이 필요한가"와 무관하다.

**처방은 결정적이다.** 같은 상태에서는 같은 처방이 나온다. 무작위로 고르면 "왜 이 문제인가"에
답할 수 없고, 사용자는 새로고침으로 마음에 드는 문제를 뽑게 된다. 밀어낸 문제는 날짜 단위로
빠진다 — 오늘 안 하겠다는 것과 영영 안 하겠다는 것은 다르다.

**스트릭은 하루 빠져도 끊기지 않는다.** 이틀 연속 빠져야 끊긴다. 하루 빠뜨렸다고 0 으로
돌아가는 규칙은 사람을 돌아오게 하는 것이 아니라 포기하게 한다. 어제를 빠뜨렸으면 오늘이
위험하다고 미리 말한다.

**3단계의 숙제를 가져갔다.** 신뢰도가 표본 수로만 정해져 있었다 — 최근성을 넣을 근거가
없어서였다. 복습 간격(7일)이 정해지면서 근거가 생겼고, 그 네 배보다 오래된 증거는 등급에는
남되 신뢰도에는 세지 않는다. 복습 간격은 `platform/common` 한 곳에 있다: Learning 이
복습 시점을 잡는 값과 Competency 가 증거의 나이를 재는 값이 어긋나면 안 된다.

**주간 리포트의 성장은 재고 있던 역량이 올라간 것만 센다.** 처음 틀린 것이 UNMEASURED →
DEVELOPING 으로 "올랐다"고 적히는 것을 실제 계정으로 보고 고쳤다. 리포트의 행동 칸은
오늘의 처방 그대로다 — 따로 지어내면 둘이 서로 다른 말을 한다.

**남긴 것.** "실수 유형" 통계는 판정 분포까지다 — 오답인지 시간 초과인지 런타임 오류인지.
변이 평가의 결함군과 최소 반례를 실수 유형으로 묶는 것은 8단계 콘텐츠와 함께 갈 자리다.
정답 직후 "다른 알고리즘·공간 개선·증명" 제안(§8.1 마지막 줄)은 해설이 있어야 하므로 7단계다.

**통과 기준**: 추천마다 이유가 붙고 사용자가 조정할 수 있다.

### 7단계. 해설·비교·실험실 — 닫힘

> 원본 §6.4~6.6. 리플레이 위에 얹혔다.

- 해설: 38문제 전부, 관찰 → 접근 → 복잡도 → 발전 과정 → 흔히 무너지는 곳. 정답 전에는
  잠기고, 명시적으로 열면 기록에 남으며 힌트 3단계와 같은 도움 단계가 된다 (FR-214)
- 비교 경기장: 한 입력에 풀이 넷까지 나란히 — 출력·연산량·메모리·최초 선택 차이 (§6.5)
- 실험실: 입력을 직접 바꿔 다시 돌린다, 시간축은 하나 (§6.6)

**셋이 하나의 요청이다.** 한 입력에 여러 풀이를 계측해 돌려 나란히 놓는 것. 해설은 참조
풀이를 사용자의 입력으로 다시 실행한 것이고, 비교는 거기에 내 풀이를 옆에 세운 것이며,
실험실은 입력을 바꿔 가며 그것을 반복하는 것이다. 실행 모드 하나(LAB)와 큐 하나로 섰다.

**완전탐색은 이미 저작돼 있었다.** 성능 오답은 답은 맞고 느릴 뿐이라 "완전탐색 → 개선 →
최적"의 첫 칸 그 자체다. 다만 계측이 없어 연산량이 0 으로, 시간은 계측 비용이 빠져
참조보다 짧게 나왔다 — 열네 개에 호출을 붙이고 전체 검증으로 오답의 성질이 그대로임을
확인했다. 최대 부분합에서 O(n²) 는 VISIT 45, O(n) 은 8 로 갈린다.

**시간은 참고로만 적는다.** 계측 실행의 시간에는 계측 비용이 섞이고, 작은 입력에서는
그 비용이 알고리즘 차이보다 크다. 연산량이 앞에 선다.

**참조 풀이의 이벤트 열이 통째로 나가는 유일한 자리다.** 그래서 잠금 확인은 LabService
한 곳에 있다 — 맞혔거나 명시적으로 열었거나. 두 곳이면 언젠가 한쪽만 고쳐진다.

**조용한 구멍을 하나 막았다.** 콘텐츠 검증 테스트가 `content/` 를 입력으로 선언하지 않아
해설 하나를 지워도 캐시에서 "통과"가 나왔다. 콘텐츠를 고친 사람이 돌리는 테스트가
콘텐츠를 보지 않으면 그 테스트는 없는 것과 같다.

**남긴 것.** 실험실의 "사용자 함수 교체"(§6.6 — 비교·휴리스틱 규칙을 사용자 코드로
바꿔 끼우기)는 참조 풀이가 그 자리를 함수로 열어 두어야 하므로 저작 규약이 먼저다.
그래프를 직접 그리는 입력 편집기도 없다 — 지금은 JSON 이다. 비교 축 중 "중복 계산"과
"최악 입력"은 이벤트만으로는 나오지 않는다.

**주의**: 비교와 실험실은 **실행 횟수를 곱한다.** 한 번에 넷, 시간에 스무 번으로 묶었다.

### 8단계. 콘텐츠 규모 — 핵심 100문제 닫힘, 분포 채우는 중 (166)

> 원본 §14.2 단계 3. 100 은 목표였지 끝이 아니다 — 문제는 계속 늘고, 이제부터는 **분포**를 본다.

- 핵심 100문제 (§10.1). 38 → 52 → 63 → 74 → 85 → 96 → 100 → **111**. 비어 있던 자리부터 — 트리·유니온파인드·큐·
  백트래킹은 0개였고, 힙·탐욕·누적합은 1개였고, CONSTRAINTS 역량은 증거를 만드는 문제가
  없었다. 셋째 묶음 열하나는 태그 분포의 빈 곳(위상 정렬·최단 경로·유니온파인드·큐·비트
  연산이 각 1개 이하)과 역량 분포의 빈 곳(READING 4, CONSTRAINTS 1, OPTIMIZATION 6)을
  겨냥했다. 넷째 묶음 열하나는 백트래킹·누적합·시뮬레이션과 READING·CONSTRAINTS 를
  더 채우고, **메모리로만 잡히는 오답**이 있는 첫 문제(가장 긴 공통 부분 수열)를 넣었다.
  다섯째 묶음 열하나는 "고전"의 빈 자리다 — 후위 표기 계산, 소행성 충돌, 최대 직사각형,
  요세푸스, 팩토리얼의 0, 정수 뒤집기, 부분 트리 크기, 트리의 지름, 최소 신장 비용,
  정렬된 격자의 k 번째, 애너그램 묶음. 여섯째 묶음 열하나는 태그 분포의 얇은 곳(큐·제자리·
  누적합·비트·정수론·위상 정렬·최단 경로·분할 정복이 각 2~5개)과 INTRO 셋·EXPERT 하나 —

**파이프라인이 실제로 걸러낸 것.** 동치 변이 하나(20만 무작위 입력에서 갈리지 않았다),
JIT 벡터화로 살아남은 O(n·k) 오답 하나(10^10 번의 max 는 2초가 안 걸린다), 작은 양수로만
시험해 해시맵 순서가 우연히 맞던 tie-break 오답 하나. 셋 다 검증 없이는 공개됐을 것이다.
content/tools/README.md 의 "오답이 살아남을 때"에 적었다.

**100 을 채우는 데 든 것.** 문제 하나가 정의 100~150줄에 해설·힌트·카탈로그이고, 전체
검증이 문제당 10~30초 — 111문제에 40분이다. 열넷, 열하나 여섯 번, 넷을 넣는 데 든 것이
그 척도다. 수는 채웠고 이제 늘리는 것은 **분포**다. 검증(VERIFICATION) 역량군의 테스트
설계·반례·디버깅은 문제의 태그가 아니라 활동(변이 평가·아레나·분기 진단)이 증거를 만든다 —
카탈로그에 0 인 것이 맞다.

**아홉째 묶음에서 검증이 걸러낸 것 — 동치 변이 둘, 성능 오답 둘.** 조상보다 작지 않은 정점의
"최댓값에 자기 값을 안 넣는" 오답은 부모의 값을 따로 더해 정답과 같았고, 가장 짧은 구간의 "같은
누적합을 큐에 남기는" 오답은 앞에서 뺄 때 둘 다 빠져 결과가 같았다 — 둘 다 진짜 실수(부모 값
빠뜨리기, 빈 접두 빠뜨리기)로 바꿨다. 마감 작업의 "힙 없이 훑는" 오답은 처음 두 번 살아남았다:
마감이 넓으면 뺄 일이 없고 촘촘하면 남은 것이 몇 없어 둘 다 빠르다. 남는 비율 f 에서 일이
n²·f(1-f)/2 라 f = 1/2 로 맞추고 걸리는 시간의 편차를 줄여야(긴 것 하나를 빼면 한참을 버틴다)
겨우 배를 넘겼고, 한도를 1/4 로 조였다. k 번째 쌍의 거리는 모든 쌍을 담는 오답이 시간이 아니라
**메모리**로만 잡혀 3배 여유가 없었다 — 담지 않고 세는 오답으로 바꾸고 n 을 2 만으로 올렸다.

**여덟째 묶음에서 검증이 걸러낸 것 — 성능 오답 셋이 살아남거나 겨우 넘겼다.** 물이 차오르는
격자의 "시각을 하나씩 올리는" 오답은 무작위 격자에서 한도의 1.2배였다 — 답이 격자가 이어지는
시각 근처라 그 뒤로 돌 BFS 가 몇 없었다. 도착 칸과 그 두 이웃에 가장 높은 셋을 두어 답을
`n²-1` 로 만들자 격자가 다 잠긴 뒤로도 수만 번 더 돌아야 했다. k 자리 지우기의 "지울 때마다
전체를 훑는" 오답은 두 번 살아남았다: 처음은 자릿수가 열 종류뿐이라 첫 내림 자리가 늘 열 칸
안에 있었고(입력 모양으로는 못 잡는다 — 전체를 훑게 바꿨다), 다음은 **JIT 가 결과에 영향 없는
순회를 통째로 지웠다** — 훑은 값을 세어 반환에 엮어야 했다. 구간 합 세기의 모든 쌍 오답은
10 만에서 2.3배라 입력을 못 키워 한도를 절반으로 조였다. 셋 다 "오답이 느리다"와 "채점기가
그것을 느리다고 판정한다"가 다르다는 것을 보여 준다.

**일곱째 묶음에서 검증이 걸러낸 것.** 회문 수의 "Int 로 뒤집어 넘친다" 오답은 **동치**였다 —
뒤집어 넘치는 수는 회문이 아니고, 넘친 값이 우연히 자기 자신일 수 없다. 둘째로 큰 값의
"둘째 초기값 0" 오답은 최댓값이 뒤에 오면 초기값이 덮여 맞는다; 최댓값이 **맨 앞**이고 나머지가
음수인 케이스가 있어야 갈렸다. 단어 사다리의 모든 쌍 비교 O(n²·L) 은 2 만 단어로는 2 초라
상한을 5 만으로 올렸고, 가장 짧은 덮는 창의 O(n²) 은 답이 어디에나 있으면 창이 금방 닫혀
빨랐다 — 답의 글자를 **맨 끝에만** 두어야 시작점마다 끝까지 갔다. INTRO 의 해설도 200자는
넘어야 한다는 게이트에 하나 걸렸다. 그리고 전체 검증에서 **이미 공개된** 격자 단어 찾기가
2.9배로 걸렸다 — 지난 검증에서 3.0 이었던 것이 머신의 흔들림만큼 내려온 것이다. 한도를 1/4
로 조이고 **버전 2** 로 올렸다; 공개된 버전은 불변이라 한도를 바꾸면 새 버전이다 (§6.1).

**마지막 넷에서 검증이 걸러낸 것.** 격자에서 단어 찾기의 성능 케이스를 "전부 A 인 격자에
A…AB" 로 잡았더니 **정답 풀이도 시간 초과**였다 — 가지치기가 마지막 글자에서만 일어나
정답도 지수적이다. 오답을 가르는 것은 글자를 **언제** 보느냐이므로, 무작위 여덟 글자 격자에
없는 단어로 바꿨다: 정답은 첫 글자에서 끊고 오답은 칸마다 3¹⁴ 갈래를 간다. 가장 긴 연속
수열의 Int 넘침 오답은 MAX 와 MIN 이 **둘 다** 있어야 갈린다 — MAX 하나로는 넘친 값이
집합에 없어 우연히 맞는다.

**여섯째 묶음에서 검증이 걸러낸 것 — 동치 변이 넷, 못 잡는 성능 변이 하나.** 최근 k개의
평균에서 "넣기 전에 내보내는" 변형은 창이 k 개로 같다. 소인수의 합에서 "p·p 를 Int 로"는
n ≤ 10⁹ 이면 p 가 31623 을 못 넘어 안 넘친다. 버전 비교에서 "자리의 차를 Int 뺄셈으로"는
음수가 아닌 두 수의 차라 안 넘친다. 풍선 터뜨리기에서 "0 인 풍선을 건너뛰는" 것은 0 을 먼저
터뜨리는 것이 최적이라 맞는 풀이다. 블록 합의 "행 누적합만" 은 O(rows·cols·k) = 6천만이라
이 제약에서는 통과한다 — 뺐다. 그리고 목록 k개 합치기의 "하나씩 합치기" O(N·k) 는 k ≤ 5000
에서 5억 번이라 안 잡혔고, k 의 상한을 N 까지 올려 원소 하나짜리 목록 20만 개로 잡았다.
INT_MATRIX 는 직사각형이라 길이가 다른 목록들을 담지 못한다 — `sizes` + `values` 로 폈다.

**다섯째 묶음에서 검증이 걸러낸 것.** 트리의 지름에서 부모 배열의 순서를 믿는 오답은
셋째 묶음과 같은 이유로 "자식이 부모보다 앞"인 사슬이 있어야 잡혔다. 최대 직사각형의
행마다 모든 열 쌍을 보는 오답은 열이 5000 이어야 3배를 넘겼고, 그래도 모자라 한도를 1/4 로
조였다. 그리고 **저작 도구 자체가 느려져 있었다** — 케이스 데이터를 `sum(..., [])` 로 펴는
것이 O(n²) 라 10만 간선 그래프 하나에 2분이 걸렸고, 전체 생성이 3분 가까이 됐다. 선형으로
바꿔 8초가 됐다. 산출물은 한 바이트도 달라지지 않았다 — 전체를 다시 뽑아 diff 가 빈 것이
그 검사다.

**넷째 묶음에서 검증이 걸러낸 것.** 동치 변이가 셋이었다 — 과반수 원소에서 "후보를 한 박자
늦게 바꾸는" 두 변형은 과반수가 보장되면 여전히 맞고, k 묶음에서 "나누어떨어짐을 안 보는"
변형은 목표를 내림하면 어차피 다 못 놓는다. 셋 다 무작위 입력 30만 개로 확인하고 진짜
실수로 바꿨다. 같은 글자 없는 부분 문자열의 O(n²) 오답은 알파벳이 작으면 창이 알파벳 크기에서
멈춰 빠르다 — 서로 다른 BMP 글자 5만 개를 이어 붙여야 잡혔다.

**셋째 묶음에서 검증이 걸러낸 것.** 방향을 뒤집은 위상 정렬 오답은 동치였다 — 층의 수는
그래프를 뒤집어도 같다. 부모 배열의 순서를 믿는 오답은 "자식이 부모보다 앞"인 케이스로도
안 잡혔다 — 부모가 루트면 아직 안 정해진 깊이의 기본값 0 이 우연히 맞는다. 잡으려면 부모가
루트가 아닌 자리가 있어야 했다. 그리고 한 칸씩 오르는 LCA 오답은 한도의 1.4배로 겨우
넘겼다 — 입력을 더 못 키워 시간을 조였다. 검증 명령에 문제를 골라 돌리는 인자를 더했다;
전체는 20분이고 새 문제 하나를 고치며 그것을 매번 기다릴 수는 없다.

### 9단계. 네트워크 — 아레나·커뮤니티·대회 열림

> 원본 §14.2 단계 4.

- **반례 아레나** (§8.3) — 열림. 오답 깨뜨리기, 자동 축소, 결함군 분류, 기록판, 그리고
  **익명화된 오답** — 남의 실제 제출을 검수를 거쳐 과녁으로 세운다
- 대회: **비레이팅 대회·미니 대결·반례 대전·가상 참가·레이팅** 섰다 (§8.4). 디비전과
  종료 후 업솔빙 표시는 표본이 쌓인 뒤
- 커뮤니티: **질문 게시판·코드 구간 링크·리플레이 시점 주석·풀이 공유·기여자 평판·
  실행 가능한 해설·단계적 제재와 이의** 섰다 (§8.5, §10.4). 남은 것은 순위표

**아레나는 변이 평가의 거울상이라 새로 지은 것이 거의 없다.** 변이 평가(4단계)는 사용자의
테스트 묶음이 오답을 얼마나 잡는지 재고, 아레나는 입력 하나로 특정 오답을 깨뜨린다. 같은
오답, 같은 참조, 같은 축소기(5단계). 다른 것은 **오답의 이름과 소스가 보인다**는 것뿐이고,
그것이 허용되는 이유는 맞힌 사람에게만 열리기 때문이다 — 오답은 정답에서 한 곳만 다른
코드라, 그것을 보는 것은 정답을 보는 것과 거의 같다.

**세 평가 축(§8.3)이 그대로 기록판이다.** 가장 작은 반례, 처음 깨뜨림, 한 입력이 깨뜨린
오답 수. 이름은 없다 — 내 것인가 아닌가만. 순위표에 이름을 올리는 것은 평판 정책(§8.5)이
서고 나서다.

**익명화된 오답은 세 단계를 거쳐 선다.** 원본이 말한 "익명화된 오답"은 남의 실제 제출이고,
익명화해도 코드는 그 사람의 것이다. 그래서 **기부**(본인만, 틀린 제출만), **검수**(REVIEWER
가 소스를 보고 결함군을 정해 세운다 — §8.3 마지막 줄의 악의적 데이터와 정답 노출 방지가 이
자리다), **신고**(맞힌 사람이 올리고 검수자가 내린다)다. 이름은 어디에도 나가지 않는다 —
과녁의 이름은 기부 id 에서 만들고, 기부자가 계정을 지우면 소스가 비어 과녁이 내려간다.

이것이 커뮤니티(§8.5)의 첫 칸이다. 질문·풀이·주석은 전부 "남의 것이 여러 사람에게 보이는"
일이고, 그 밑바닥이 신고와 검수다. 아레나의 오답으로 먼저 세운 이유는 그것이 이미 있는
과녁의 자리에 꼭 들어맞아 새로 지을 화면이 거의 없었기 때문이다. 검수는 재채점 승인과
같은 REVIEWER 다 — 둘 다 "다른 사람에게 영향을 주는 결정을 한 번 더 보는" 역할이다.

**둘째 칸은 질문 게시판이고, 원본의 세 줄(질문 게시판·코드 구간 링크·리플레이 시점 주석)이
글 하나의 모양이다.** 질문과 답은 같은 표의 글이고, 글에는 **자기 제출의 한 자리** —
줄 범위, 리플레이의 걸음, 또는 둘 다 — 를 붙일 수 있다. 붙인 코드 구간은 붙인 시점의
줄들로 글에 실려 나가고(40줄까지 — 그보다 길면 구간이 아니라 풀이 전체다), 붙인 리플레이는
그 글을 볼 수 있는 사람이 연다. 그래서 제출 도메인에 첫 예외가 생겼다: 제출은 소유자의
것인데, 게시판에 붙어 공유된 제출의 **판정과 트레이스**는 남에게 열린다. 소스와 분기 진단,
예측, 반례 줄이기, 내놓기는 열리지 않는다 — 그것은 푸는 사람의 증거다. 누가 무엇을
붙였는지는 게시판이 알고 제출 도메인은 묻기만 한다(§3.1 조립 지점 하나).

잠금은 아레나와 같다. 글쓴이가 **풀이 노출**이라고 표시한 글의 본문과 붙인 자리는 맞힌
사람에게만 열리고, 제목은 잠기지 않는다 — 무엇을 묻는지는 맞히기 전에도 보여야 "이미 물은
것인가"를 알 수 있다. 신고는 보는 사람이면 누구나(아레나와 달리 맞힌 사람만이 아니다 —
글은 맞히기 전에도 보이므로), 내리는 것은 같은 REVIEWER 다. 계정을 지우면 본문과 붙인
자리가 비고 글은 남는다 — 답이 달린 질문을 지우면 남의 답이 허공에 뜬다.

**검증이 잡은 것.** 새 경로를 인증 인터셉터의 목록에 넣지 않았고, 그러면 모든 요청이
principal 없이 400 이다. "남의 제출은 붙이지 못한다: 400" 검사가 **엉뚱한 이유로 초록**이었다.
스모크는 이제 그 절을 "토큰 없는 요청 거부"로 시작한다 — 거절을 검사하기 전에 거절의
이유가 맞는지 먼저 본다. 스모크 194/194.

**셋째 칸은 풀이 공유와 기여자 평판이고, 풀이는 새 표가 아니라 글 한 종류다.** 맞힌 제출에
접근을 적어 올리는 글(`kind = SOLUTION`)이고, 보이는 것·신고·내림·삭제가 전부 글과 같다.
다른 것은 셋 — 붙이는 제출이 맞힌 것이어야 하고, 코드 구간이 아니라 소스 전체(400줄까지)
이며, 항상 풀이 노출이다. 코드만 올리는 것은 풀이가 아니라서 접근 설명 30자가 관문이다.
못 맞힌 사람에게는 제목과 도움됐다 수만 보인다 — 어떤 접근이 있는지는 맞히기 전에 보여도
되지만 코드는 아니다.

평판은 **남이 판단한 것**으로만 잰다. 맞힌 사람이 남의 글에 한 번 남기는 "도움됐다"의 수에,
아레나에 세워진 기부(내려지면 빠진다)를 3 배로 더한 것이 점수이고, 글을 많이 쓰는 것 자체는
점수가 아니다. 수치는 본인에게만 보이고 남에게 나가는 것은 등급(새 기여자·기여자·믿을 만한
기여자)뿐이다 — 이름은 여전히 어디에도 없다. 순위표는 아직 없다; 그것은 이름을 내는
정책과 함께 온다. 도움됐다를 남긴 기록은 계정을 지우면 지워지고, 받은 것은 글에 남는다.
스모크 213/213.

**"실행 가능한 인터랙티브 해설"은 새 화면이 아니라 실험실의 후보 하나다.** 공유된 풀이가
맞힌 사람의 실험실에 "공유 풀이: <접근>" 으로 서고, 참조 풀이·내 풀이와 같은 입력에서
나란히 돈다 — 출력·연산량·메모리·이벤트 열이 한 표에 놓인다. 저작자의 해설이 "왜 맞나"
라면 이것은 "다른 접근은 어디가 다른가"다. 해설을 정답 전에 연 사람에게는 서지 않는다 —
그 사람은 참조 풀이까지 본 것이지 남의 코드까지 본 것은 아니다. 실험실은 풀이가 어디서
왔는지 모른다; 이름·언어·소스만 받는다(§3.1 조립 지점 하나). 스모크 228/228.

**Kotlin 제출만 내놓을 수 있다.** 아레나가 오답을 돌리는 길이 저작자의 대표 오답과 같은
Kotlin 컴파일이라서다. 다른 언어의 오답은 그 길이 생길 때 열린다.

**대회는 시작하지 않았다.** 전제가 §11.4 부정행위 방어다. 그 밑바닥인 워크로드 신원(A4)과
컴파일 격리(A5)는 섰고, **제출 사이의 유사도 신호**, **단계적 제재·이의**, **가입·로그인
한도**(A6 의 남은 절반)까지 섰다. 방어 없이 순위를 매기면 순위가 먼저 망가지고 그 다음에
제품이 망가진다 — 그 방어가 이제 다 있다.

**대회는 비레이팅과 미니 대결부터다.** 레이팅은 순위가 믿을 만해진 뒤의 일이고, 순위가 믿을
만한지는 비레이팅으로 먼저 본다. 대회는 운영자가 만들고(CONTENT_EDITOR) 다른 사람이 연다
(PUBLISHER — 문제 공개와 같은 2인 원칙). 미니 대결은 사용자가 문제 하나로 열고, 코드를 받은
한 사람이 붙는 순간 시작한다 — 짧은 문제를 동시에 풀고 끝난 뒤 순위표를 본다. 점수는 판정에서
온다: 판정이 확정되면 조립 지점이 대회에 알리고, 대회는 "참가 중이고 돌고 있으며 이 문제를 건
대회"에만 문제별 최고 점수를 적는다. 창은 제출 시각으로 본다 — 판정이 늦어도 제출은 대회 안이다.
대회 밖의 제출은 대회와 무관하다; 문제는 그대로 문제다.

**참가가 곧 이름 공개 동의다.** 이 제품은 여기까지 이름을 어디에도 내지 않았다. 순위표는
이름 없이는 뜻이 없으므로, 참가할 때의 표시 이름을 그 대회의 순위표에만 낸다 — 버튼이 그
말을 미리 한다. 계정을 지우면 이름 없는 줄이 된다; 점수는 남의 순위에 얽혀 있어 남는다.
글쓰기 정지 중에는 참가도 대결도 못 한다 — 순위표에 이름을 올리는 것도 쓰기다. 스모크
276/276 — 열두 절이 되면서 한 번에 11분이다.

**반례 대전은 아레나 위의 대회 종류다.** 문제를 맞힌 뒤(아레나의 잠금이 그대로다) 대회 중에
깨뜨린 **서로 다른 과녁의 수**가 점수이고, 정답 자체는 점수가 아니다. 아레나가 시도의 결과를
학습 기록에 알리던 신호에 "무엇을 언제 깨뜨렸나"를 더해 같은 조립 지점에서 대회로 흘린다 —
아레나는 대회를 모른다. 같은 과녁을 두 번 깨뜨리는 것은 한 번이고, 동점은 그 수에 먼저 이른
쪽이 앞이다. 스모크 279/279.

**가상 참가는 끝난 대회를 혼자 다시 도는 것이다.** 같은 문제, 같은 길이로 지금부터 돌고,
순위표는 **원래 참가자들 사이의 내 자리**다 — "그때 참가했다면 몇 등이었나". 그래서 순위의
동점은 시각이 아니라 **각자의 시작에서 잰 시간**으로 가른다; 다른 날 돈 사람과 같은 시간
조건으로 견주는 길이 그것이다. 원래 순위표는 건드리지 않고 가상 참가는 남에게 없다. 돌고
있는 것이 있으면 새로 열지 않는다. 스모크 286/286. 스모크가 잡은 것: 짧은 대회의 창을 절
첫머리의 시각으로 잡았더니 아레나 시도가 시간을 먹어 참가하기 전에 끝나 있었다 — 창은
쓰는 자리에서 잰다.

**레이팅은 재계산 가능한 projection 이다.** 레이팅 대회(`rated`)가 끝나면 순위표에서 여러
명의 Elo 를 한 번 적용한다 — 참가자마다 나머지 전원과의 기대 승률을 평균하고 실제 순위와의
차에 K=64 를 곱한다. 둘이면 보통의 Elo 이고 많아도 변화가 참가자 수에 따라 부풀지 않는다.
변화는 전부 남아 사용자의 레이팅은 그 합이다 — 식이 잘못됐으면 변화를 지우고 다시 센다
(원본 §10.2 "표본 이후 보정"). 적용은 순위표를 처음 여는 순간 또는 1분 주기의 훑기에서
한 번만 — `rated_at` 이 잠금이다. 처음은 1500, 첫 다섯 대회는 잠정으로 표시한다. 레이팅
대회를 여는 것은 여전히 운영자의 결정이고, 비레이팅의 순위가 믿을 만해 보인 뒤다 — 코드가
있다는 것과 여는 것은 다른 일이다. 스모크 293/293. 스모크가 잡은 것: 문제가 111 이 되며 한
페이지(100)를 넘어 `two-sum` 이 둘째 페이지로 갔고, 목록을 한 페이지로 읽던 검사 둘이
떨어졌다 — 커서를 따라 끝까지 읽게 했다.

**제재는 세 단계이고 근거를 가리킨다.** 경고(기록), 글쓰기 정지(질문·답·풀이·기부·신고),
제출 정지(실행 전부 — 글쓰기도 함께). 기간이 있고 영구 정지는 없다 — 그것은 삭제이고 삭제는
본인만 한다. 발부는 SECURITY_ADMIN 이 `similarity:<id>` 나 `report:<id>` 를 들어 한다; 근거
없는 제재는 없다. 막는 곳은 **문 앞**([AuthInterceptor]) — 인증과 같은 이유로 엔드포인트가
아니라 경로로 건다: 새 쓰기 경로를 만든 사람이 제재를 잊어도 열리지 않아야 한다. 읽기는
전부 열린다; 제재 중에도 자기 판정과 남의 글은 보고, **이의는 낸다** — 정지 중에 열려 있는
유일한 쓰기다. 이의는 제재 하나에 한 번이고 **발부한 사람은 판단하지 못한다** — 재채점
승인과 같은 2인 원칙이다. 받아들여지면 그 자리에서 풀리고, 답은 본인의 화면 맨 위에 실린다.
스모크 250/250.

**검증이 고친 것.** 유사도 큐를 점수순으로 뒀더니 스모크를 되풀이하자 오래된 1.0 들이 큐를
채워 새 신호가 영영 보이지 않았다 — 새 것부터로 바꿨다. 점수는 같은 자리에 실려 있다.

**유사도 신호는 판정이 아니다.** 맞힌 제출이 확정되면 소스의 **구조 지문**을 뜬다 — 주석을
지우고 식별자·숫자·문자열을 각각 한 토큰으로 접은 뒤 토큰 다섯 개씩의 해시를 창마다 하나씩
고른다(winnowing). 이름을 바꾸고 주석을 붙여도 지문은 같고, 다른 접근은 다르다(테스트가 둘
다 확인한다). 같은 문제·같은 언어의 **다른 사람** 지문과 자카드 유사도가 0.8 을 넘으면 쌍이
검수 큐에 오르고, 검수자가 두 소스를 나란히 보고 확인하거나 기각한다. 확인해도 판정과 계정은
그대로다 — 원본 §10.4 "탐지 신호를 단독 유죄 근거로 사용하지 않고 이의 절차를 제공한다"가
그 이유고, 제재는 정책과 함께 온다. 40 토큰 아래의 소스는 뜨지 않는다; 한 줄짜리 풀이는 누가
써도 같다. 새 모듈 `integrity` 는 소스를 갖지 않는다 — 지문만 갖고, 소스는 검수자가 볼 때
제출 도메인에 묻는다. 스모크 223/223.

**전제**: 커뮤니티는 신고·제재(§8.5)가, 대회는 §11.4 가 먼저 있어야 한다.

죽었다. 1초마다 제어 영역을 두드리는 감시로 잡아 보니 제어 영역의 스레드가 Postgres 의 응답을
기다리고 있었고, 같은 머신에서 다른 저장소의 테스트가 testcontainers 로 돌며 Docker VM 의
메모리를 다 쓰고 있었다 — 샌드박스의 Kotlin 컴파일까지 exit 137 로 죽어 멀쩡한 풀이가
COMPILE_ERROR 를 받았다. 스택의 문제가 아니라 머신의 문제였다. 죽은 스모크가 남긴 세워진
과녁이 다음 스모크의 "검수 전에는 과녁이 아니다"를 깨뜨렸고 — 스모크는 자기 과녁을 끝에
내리는데 죽어서 못 내렸다 — 그것을 내리고 머신이 한가할 때 돌린 것이 319/319 였다. 스모크의
10초 한도는 한가한 머신의 것이다.

Java·초안·재채점·대회를 더한 뒤의 첫 완주는 프로젝트 절에서 넷이 무너졌고, 셋은 스모크의 낡은
가정이었다 — 공개 프로젝트가 하나라는 가정(`[0]`), 대회 생성 응답에 problemCount 가 있다는

제출을 "null → ACCEPTED" 로 바뀐 판정에 넣었다. 비교할 이전 판정이 없으면 바뀐 것이 아니다.
고치고 돌린 것이 351/351 — 부하 평균 16 인 머신에서였다. 프로젝트 여덟·문제 147 뒤의 완주는 353/353.

**Kotlin 을 붙이며 걸러낸 것.** 하네스 클래스를 못 찾는 RUNTIME_ERROR — `List<Path> + Path` 가
경로를 조각으로 펼쳐 클래스패스가 `…/private:…/var:…/folders` 가 됐다(Path 는 Iterable<Path>);
알고리즘 어댑터가 `plusElement` 를 쓰는 이유를 다시 배웠다. 숨은 테스트 둘의 기대가 틀려
참조가 떨어졌다 — 조회가 순서를 바꾼다는 규칙을 테스트 자신이 어겼다. tamper 오답이 프로세스
샌드박스에서는 잡히고 컨테이너에서는 평범한 오답이었다 — 상대 경로 `out/report.json` 이
컨테이너의 작업 디렉터리(`/tmp`)에서는 없는 곳이었다. 인자에서 경로를 찾게 바꾸자 둘 다 가드가
잡았다. "가드가 잡았다"는 저작 검증(프로세스)에서만 본 것이었고, 실제 스택(컨테이너)에서 다시
봐야 했다.

**넷을 놓으며 검증이 걸러낸 것.** 토큰 버킷의 "지난 시간을 정수로 내림" 오답은 숨은 테스트가
시계를 정수 초로만 돌려서 살아남았다 — 0.5초를 돌려야 갈렸다. "용량에서 자르지 않음" 오답은
처음 보는 키가 어차피 가득 차 있어 살아남았다 — 비운 뒤 오래 쉬어야 상한이 시험된다. 둘 다
"테스트가 무엇을 가정하고 있나"를 오답이 되짚어 준 경우이고, 알고리즘 문제의 동치 변이와
같은 종류의 발견이다. 그리고 네 문제가 재는 것이 보이기 시작했다 — 요구사항의 **경계 조건을
코드로 옮기는 정확성**(거절은 상태를 바꾸지 않는다, 실패한 편집은 편집이 아니다, 줄 번호는
사람의 것이다)이 넷에 공통이고, 그것이 온톨로지의 어느 칸에도 없다는 것도.

*재채점*: 알고리즘 재채점과 **같은 작업·승인·대상·감사**를 탄다 — scope 만 `project:<id>` ·
`project-submission:<uuid>` 로 다르고, Admin 의 재채점 서비스가 같은 포트(`JudgedSubmissions`)를
프로젝트 쪽에 하나 더 잇는다. 판정 이력(`project_judgement`)과 revision 도 같은 규칙: 종착은
불변, dry-run 은 이력에만, 승인 없이 온 뒤늦은 결과는 반영하지 않는다. 재채점은 증거를 쌓지
않는다. 재채점 전에 스토어의 워크스페이스를 훼손해 두고 돌려 DB 의 파일로 다시 올라가는 것을
확인했다. 대상 표의 외래키는 풀었다 — 대상은 두 판정기의 제출이라 한 표를 가리킬 수 없다.

*Kotlin*: 둘째 언어. 알고리즘 판정의 Kotlin 어댑터와 같은 컴파일러·런타임 jar 를 샌드박스에
들여보내 워크스페이스 전체와 하네스를 한 번에 컴파일한다(한 번에 2~3초). 테스트 기반은
kotlin-test 가 아니라 하네스의 단언 몇 개 — 샌드박스에는 표준 라이브러리뿐이다. 첫 문제는
만료가 있는 LRU 캐시. 언어를 늘리며 가드가 하나 더 붙었다: **리포트의 nonce**. 하네스가 사용자
코드를 들이기 전에 읽고 지운 값을 리포트에 싣고 채점기가 대조한다 — 리포트 경로는 프로세스
인자에 있어 사용자 코드가 꾸며 쓸 수 있지만 nonce 는 모른다. Kotlin 의 tamper 오답이 정확히
그것을 한다: 인자에서 리포트 경로를 찾아 전부 통과로 쓰고 프로세스를 끝낸다.

*대회*: 프로젝트형 문제도 문제라 대회에 들어간다 — 공개된 id 면 대회 문제로 받고, 판정이 오면
알고리즘 제출과 같은 자리에서 같은 창(제출 시각)으로 점수를 적는다. 화면은 대회의 문제 목록에서
프로젝트 id 를 눌렀을 때 문제 화면이 아니라 프로젝트 패널을 연다 — 어느 쪽인지는 공개된
프로젝트 목록이 가른다.

*Java*: 셋째 언어. JDK 이미지의 javac 로 워크스페이스 전체와 하네스를 한 번에 컴파일한다(0.5초).
하네스와 단언은 Kotlin 의 것을 Java 로 옮긴 것 — 같은 약속, 같은 nonce 가드. 첫 문제는 계좌와
이체. *업로드*: 편집기에 파일·폴더 가져오기. 서버는 모르고, 제출·초안은 그대로 파일 묶음이다.
숨은 파일과 256KB 를 넘는 파일은 건너뛰고 그 사실을 말한다.

*둘째 묶음*: 언어마다 둘이 되도록 Kotlin·Java 하나씩 — 회의실 예약(반열린 구간의 겹침, 자기
자신과 부딪히지 않는 옮기기, 실패해도 남는 원래 예약), 경로 라우터(글자 조각이 매개변수를 이기는
전순서, 끝의 슬래시와 질의 문자열의 정규화, 이름만 다른 패턴은 같은 모양). 검증이 잡은 것 —
Kotlin 의 tamper 오답이 살아남았다: 파일 최상위 `val` 은 그 파일의 facade 클래스가 참조될 때만
초기화되고, 아무도 참조하지 않으면 리포트를 꾸며 쓰는 코드가 돌지 않는다. 첫 Kotlin 문제가
메서드 안에서 그 값을 읽는 이유였다. 실제 스택에서 참조·오답·tamper 를 제출해 ACCEPTED·
WRONG_ANSWER(숨은 8/9, 6/9)·WRONG_ANSWER(0/1) 를 확인했다.

*셋째 묶음*: 장바구니 가격 계산(Python, EASY — 수량 할인은 줄마다, 쿠폰은 소계에 한 번, 전부 내림;
`999 + 501` 처럼 줄마다 내림한 합과 소계에 한 번 내림한 값이 갈리는 금액을 골라야 순서 위반 오답이
잡혔다)과 주차장(Java, MEDIUM — 맞는 자리 중 가장 작은 것, 30분 이하 무료 뒤 시작한 시간 단위,
요금은 차가 아니라 댄 자리의 것). Python 다섯, Kotlin 둘, Java 셋. Python 의 순환 import(`__init__` 이
`cart` 를 먼저 들여오고 `cart` 가 `pricing` 의 예외를 찾는다)는 검증이 `<import>` 실패로 잡았다 —
예외를 `errors.py` 로 뺐다.

*실무군 셋째 역량 — 결함 검출(`DEFECT_DETECTION`)*. "잴 수 있는 것이 보일 때 늘린다"고 적어 두었던
자리다. 테스트 작성은 "썼고 통과했다"까지만 잰다 — 통과만 하는 테스트는 아무것도 잡지 못하는 테스트일
수 있다. 이제 더 쓴 테스트를 **참조 구현과 대표 오답 위에서** 돌린다: 참조에서 통과해야 하고(틀린
것을 기대하는 테스트는 테스트가 아니다), 오답의 절반 이상을 떨어뜨리면 성공이다. 저작 검증이 요구해
온 `mutants/` 가 그대로 시험판이 되어 검증의 도구에서 채점의 일부가 됐다. 같은 요청·같은 임대다 —
`ProjectRequest` 에 시험판 참조 하나, `ProjectResult` 에 결과 한 칸이 붙었고 큐도 표도 새로 두지
않았다(열 하나씩). Runner 는 더 쓴 테스트가 있을 때만 돌리고, 사용자의 **테스트 파일만** 판 위에
얹는다 — 구현은 시험 대상이 아니다. 오답의 내용은 나가지 않고 이름과 수만 나간다; 이름은 무엇을 놓쳤는지의
힌트다. 스모크: 아무것도 못 잡는 테스트는 실패 증거, 로트 나머지를 묻는 테스트는 partial-lot 과 lifo
둘을 잡아 성공, 틀린 것을 기대하는 테스트는 참조에서 떨어지고 자기 제출도 오답이다. 완주 362/362.

그 완주가 채점의 구멍을 보였다: 사용자의 테스트 파일에는 **공개 테스트가 그대로** 들어 있어 사소한
테스트 하나만 더 써도 공개 테스트가 잡던 오답이 전부 "내가 잡은 것"이 됐다 — 없는 SKU 의 재고가 0
이라는 테스트 하나로 넷 중 둘. Runner 는 이제 떨어진 오답마다 판을 손대지 않은 채 한 번 더 돌려
공개 테스트만으로도 떨어지는 것을 사용자의 몫에서 뺀다. 그러면 공개 테스트가 다 잡는 문제는 이
역량을 재지 못하므로 저작 검증에 probe-room(공개 테스트 너머의 오답이 둘은 있어야)을 두었다 — 열
프로젝트가 2~4개. 파이프라인 6, 164개 재검증·재공개. 재고 원장의 내 몫은 되돌리기와 이력이다. 완주 363/363.

*넷째*: 버전이 있는 키-값 저장소(Kotlin, MEDIUM) — 결함 검출을 염두에 두고 지은 첫 문제다. 지우기는
이력에 "없음"을 적는 것이고 되감기는 새 버전이라, 공개 테스트가 못 잡는 오답이 넷(지우기가 이력을
없앤다, 되감기가 이력을 자른다, 같은 값은 버전을 건너뛴다, 없는 키를 지울 때 버전을 먼저 올린다)이다.
실제 스택에서 "지운 뒤 지난 버전이 읽히는가"를 묻는 Kotlin 테스트 하나가 그 오답 하나를 잡고, 공개
테스트가 잡던 등호 오답은 내 몫에서 빠졌다. 순위표(Java, MEDIUM — 경쟁 순위 1, 2, 2, 4; 동점은 이름
순; 초기화는 0 점으로 남기기; 거절되는 요청은 흔적을 남기지 않기)는 공개 테스트 너머의 오답이 다섯이다.
분·시 일정식(Python, MEDIUM — 간격은 범위의 시작에서, 다음 실행은 엄격히 뒤, 하루를 넘으면 다음 날,
뒤집힌 범위와 값에 붙은 간격은 거절)은 공개 테스트 너머의 오답이 다섯. 그 확인 중 브로커 컨테이너가
이미지 빌드의 메모리 압박으로 죽었다(137)가 살아났고, 큐에 있던 제출은 그대로 이어 채점됐다 —
아웃박스와 재접속이 일한 것이다. Python 여섯, Kotlin 셋, Java 넷. 작업 공간의 제출 버튼 옆에 "테스트를 더 쓰면 그 테스트가 대표 오답을
잡는지도 잽니다" 한 줄을 두었다 — 본문 열둘을 고치는 대신 모든 프로젝트에 같은 자리다.

**아직 없는 것**: 없다. 프로젝트형은 언어 셋에 초안·재채점·대회·가져오기까지 섰다. 늘리는 것은
문제다. 편집기는 처음에 문제 목록 아래의 패널이었다 — 파일 여럿과 긴 요구사항이 왼쪽 열
한 칸에 들어가 편집기가 300px 남짓이었다. 이제 프로젝트를 열면 **두 열 화면을 통째로 작업
공간이 대신한다**(`ProjectWorkspace`): 왼쪽에 요구사항과 내 제출, 오른쪽에 파일 탭·편집기·
판정. 두 열은 지우지 않고 감춘다 — 알고리즘 문제의 초안과 편집기 상태가 그대로 남아 목록으로
돌아오면 하던 자리다. 처음 여는 파일은 `TODO` 가 있는 파일이다(시작 저장소가 고칠 자리를 그렇게
비워 둔다); 이름 순의 첫 파일은 대개 모델 선언이었다. 공개 테스트 파일 이름이 언어와 무관하게
`.py` 로 찍히던 것도 이때 고쳤다.

**봉투를 늘리지 않고 하나 더 둔다.** `ExecutionRequest` 에 파일 목록 칸을 붙이면 Runner 의
모든 어댑터가 "파일이 하나인가 여럿인가"를 분기해야 하고, 그 분기는 첫 판정기의 격리·측정을
건드린다. 격리·임대·fencing 은 다시 쓰되 요청과 채점 규칙은 따로 둔다 — 7단계가 LAB 모드를
같은 봉투에 넣을 수 있었던 것은 소스가 여전히 하나였기 때문이다.

**과정 증거는 트레이스가 아니라 변경 기록이다.** 계측 SDK 는 함수 하나의 실행을 이벤트로
남기지, 저장소를 며칠에 걸쳐 고치는 일을 남기지 않는다. 여기서 "왜 그렇게 동작하는지"에
답하는 것은 무엇을 언제 고쳤고 언제 테스트를 돌렸는가이며, 그것은 10단계 §7.3 AI 협업
리플레이가 요구하는 "계획·변경·테스트 기록"과 같은 기판이다. **어느 쪽을 먼저 짓든
기판은 하나여야 한다** — 둘이면 같은 제출의 과정이 두 벌로 기록되고 서로 다른 말을 한다.

**전제**: B3 오브젝트 스토어. 소스 전문을 메시지에 싣는 지금 방식은 파일 하나에서도 이미
문제로 적혀 있고([production-readiness.md](production-readiness.md) B3), 저장소 하나를
브로커 메시지에 실을 수는 없다. 표절·공모 탐지(A6 의 남은 절반)는 개인 학습에는 전제가
아니지만 12단계 기업 평가로 넘길 때는 전제다 — 가져가서 푸는 과제는 시험장이 아니다.

**이 단계가 아닌 것**: SQL 저지와 인터랙티브 저지. 기술 설계서 §1.1 이 따로 뺐고, 각각 또
다른 판정기다. 10단계 AI 모드에 의존하지도 않는다 — Plan → Delegate → Verify(§7.2)는
함수 하나보다 저장소에서 뜻이 있어 프로젝트형이 그 자연스러운 무대이지만, AI 없이 채점되는
것이 먼저다.

**통과 기준**: 프로젝트형 문제 하나가 저작 검증을 지나 제출·채점·증거까지 알고리즘 문제와
같은 경로를 탄다. 숨은 테스트가 API 로 새지 않는다. — **지났다.** 저작 검증·제출·채점·증거
까지 한 경로이고, 숨은 테스트는 API 어디에도 없다(스모크가 상세와 결과에서 확인한다).

### 12단계. 교육기관·기업

> 원본 §9, §14.2 단계 5.

- 교육기관: 비공개 그룹, 과제·마감, 학급 전체의 최초 분기점 분포, 시험 중 기능 제한
- 기업 평가: 평가 템플릿, AI 모드 구성, 과정 기록 제공, 면접에서 리플레이 재생.
  프로젝트형 문제는 11단계에서 온다
- 장기 실무형: 레거시 고고학, 변경 영향 예측, 요구사항 정합성, 장애 대응, AI PR 승인, 사양 저지

**원본의 경고**(§15.1): "B2B 요구가 소비자 학습 경험을 훼손하면 실행 인프라는 공유하되
제품 표면을 분리한다."

## 4. 인프라는 어디에 끼는가

[production-readiness.md](production-readiness.md)의 A4(워크로드 신원)·A5(컴파일
격리)·B3(오브젝트 스토어)는 **기능이 아니라 규모의 전제**다. 끼는 자리는 이렇다.

| 무엇이 그것을 요구하나 | 항목 |
|---|---|
| 2단계 커스텀 테스트 — 실행량이 몇 배로 는다 | ~~A5 컴파일 격리~~ 닫힘 |
| 7단계 비교·실험실 — 다시 몇 배 | ~~A5, 노드 여럿 → A4~~ 닫힘 |
| 8단계 콘텐츠 100문제 — 테스트가 메시지 한계에 닿는다 | ~~B3 번들~~ 닫힘 |
| 11단계 프로젝트형 문제 — 저장소 하나는 메시지에 실리지 않는다 | ~~B3 의 남은 절반(소스)~~ 닫힘 |

**배포 대상은 앱 호스트 하나 + Runner 노드 하나로 정했다** (2026-09). Runner 노드마다
compose 한 벌과 신원 하나라는 지금 모양 그대로이고 매니페스트는 짜지 않는다. 그 결정으로
A7 의 자동화(15분 덤프·밖으로 복사·매일 리허설)와 인증서 만료 감시·갱신이 붙었다. 3배 여유 재측정은 그 Runner 노드가
실제로 생길 때 거기서 `validateContent` 를 한 번 돌리는 것이다.

## 6. 다음 한 걸음

**9단계와 11단계가 닫혔다.** 아레나·커뮤니티·대회와 그 전제인 §11.4 부정행위 방어가 다 섰고,
두 번째 판정기 — 봉투·큐·채점 규칙이 따로인 프로젝트형 판정 — 가 문제 넷으로 저작 검증·제출·
채점·증거를 지난다. 역량군을 하나 늘린 것이 그 마지막 조각이었다.

- **AI 협업 모드**(10단계)는 원본이 스스로 게이트를 걸었다: 저지가 안정되기 전에는 시작하지
  않는다. 부하 시험(§12.1)이 목표 하드웨어에서 돌아야 그 게이트가 열린다.
- **프로젝트형**(11단계)은 통과 기준을 지났고 언어가 셋(Python·Kotlin·Java)이며 초안·재채점·
  대회·가져오기까지 섰다. 남은 것은 문제를 늘리는 것뿐이다.
- **교육기관·기업**(12단계)은 수익화이고, 원본은 "지표 충족 후"라고 적었다. 프로젝트형
  판정기는 그쪽의 전제였고, 이제 섰다.

인프라 쪽의 다중 노드는 **compose 로** 섰다 — 앱 스택 한 벌, Runner 노드마다 한 벌과
인증서 하나. 임대는 Redis 에 있어 오케스트레이터도 여럿일 수 있다. 배포 대상을 그 모양
그대로(앱 호스트 하나 + Runner 노드 하나)로 정했으므로 매니페스트는 짜지 않는다. 백업
자동화는 붙었고, 3배 여유 재측정과 Redis·스토어의 가용성은 머신이 생긴 뒤의 일이다.

테스트 번들·제출 소스·프로젝트형의 워크스페이스와 숨은 스위트는 오브젝트 스토어로 갔다 (B3).
메시지에는 참조와 digest 만 실리고, DB 의 소스와 파일은 화면·공유·신호의 것으로 남아 스토어의
실행용 복제를 언제든 다시 만든다 — 그래서 재채점·삭제는 함께 움직였고 백업은 늘지 않아도 됐다.
"DB 의 전문을 참조로 바꾸는 것"은 하지 않기로 했다: 프로젝트형에서도 파일은 DB 에 남는 쪽이
맞았다 — 화면과 반출이 그것을 읽고, 스토어는 실행의 것이다.

배포 대상은 **앱 호스트 하나 + Runner 노드 하나**로 정했다. 그 뒤에 줄 서 있던 것 중
코드로 할 수 있는 것(백업 자동화, 인증서 만료 감시와 갱신)은 붙였고, 남은 것은 머신이
생겨야 하는 것 — 그 Runner 노드에서의 3배 여유 재측정, 경보 수신자 — 이다. 현재 커밋의 이미지 넷을 로컬에서
만들어 기동 확인과 취약점 게이트를 지났다(게이트가 잡은 netty CRITICAL 은 고쳤다 —
production-readiness B4). 결함 검출·프로젝트 열둘·문제 160 뒤에 같은 것을 다시 돌렸다: 전체 빌드
214 테스트(건너뜀 0), 이미지 넷 빌드·기동·게이트 통과(프로젝트 12·문제 160 이 구워져 있다). 그래서 다음 한 걸음은
**머신을 마련해 deploying.md 의 절차대로 첫 배포를 하는 것**이다 — 양쪽 호스트에서
`scripts/preflight.py` 가 전제와 결과를 본다 — 코드로 할 수 있는 것은 여전히
8단계의 분포 채우기와 프로젝트형 문제 늘리기다.

콘텐츠는 166문제 + 프로젝트형 13문제(Python 여섯, Kotlin 셋, Java 넷)다. 넷이 공통으로 재던 것 — 요구사항의 경계 조건을 코드로
옮기는 정확성 — 이 실무군의 첫 역량이 됐고, 테스트 작성이 둘째, 결함 검출(더 쓴 테스트가 대표 오답을
잡는가)이 셋째다. 이제부터 늘리는 것은 난이도·태그 분포의 빈 곳과 프로젝트형의 언어별 수다.
