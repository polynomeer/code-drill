# 문제 저작 도구

> **역할**: 문제 패키지를 만들고 다시 뽑는 방법
> **단일 출처**: 저작 절차와 케이스 데이터 생성 규칙
> **갱신 트리거**: 카탈로그 모듈이 늘거나, 패키지 스키마가 바뀔 때

**패키지가 산출물이고 이 도구는 저작 수단이다.** 진실의 원천은 언제나
`content/problems/<id>/` 아래의 파일이며, 공개된 버전은 digest 로 고정된다 (§6.1).

```bash
python3 content/tools/author.py            # 전체 생성
python3 content/tools/author.py two-sum    # 하나만
python3 content/tools/author.py --status   # 문제 × 산출물 표 — 무엇이 비었나
./gradlew :judge:runner-agent:validateContent
./gradlew :judge:runner-agent:validateContent --args='content/problems content/reports two-sum,move-zeros'
```

마지막 줄은 **저작 중에만** 쓴다. 전체는 문제당 10~30초라 새 문제 하나를 고치며 매번 전체를
기다릴 수 없다. 고른 문제의 보고서만 다시 쓰고 나머지는 그대로 둔다 — 공개 앞에는 언제나
전체다.

**정의가 진실의 원천이다.** 정의에서 뺀 케이스와 오답은 파일도 함께 지워진다. 생성된
파일을 손으로 고치면 다음 생성에서 사라진다 — 7단계에서 성능 오답에 붙인 계측이 그렇게
한 번 사라졌다. 고칠 것은 `catalog_*.py` 다. 전체를 다시 뽑아 `git diff` 가 비는 것이 그
규칙이 지켜졌다는 검사다.

새 문제를 처음 뽑으면 손으로 쓰는 세 산출물(`catalog.yaml`·`hints.yaml`·`editorial.md`)의
자리를 TODO 로 잡아 준다. 채우기 전에는 검증을 통과하지 못한다.

## 두 구현이 서로를 검증한다

기대 출력은 카탈로그의 **파이썬 참조 구현**이 계산하고, 채점은 패키지의 **코틀린 참조
구현**이 통과하는지로 검증한다. 두 구현이 어긋나면 §6.3 의 `official-solution` 검사가
실패한다 — 서로 다른 두 사람이 같은 문제를 푼 셈이라, 한쪽의 착각이 조용히 정답으로
굳는 일이 없다.

## 패키지에 무엇이 들어가나

| 파일 | 무엇 | digest 에 드나 |
|---|---|---|
| `manifest.yaml` | 제한·시그니처·그룹 정책 | **든다** |
| `tests/<group>/*.json` | 케이스 | **든다** |
| `statement.md` | 지문 | 안 든다 |
| `solutions/reference.kt` | 참조 풀이 | 안 든다 |
| `mutants/*.kt` | 변이 구현 | 안 든다 |
| `catalog.yaml` | 난이도·태그·역량·선수 관계 | **안 든다** |
| `hints.yaml` | 코칭 도움 사다리 | **안 든다** |
| `editorial.md` | 해설 | **안 든다** |

`packageDigest` 는 **판정을 재현하는 근거**다. 이미 등록된 버전과 digest 가 다르면 등록이
거절되고, 고친 패키지는 새 버전이어야 한다 (§6.1).

그래서 카탈로그와 힌트는 밖에 있다. 난이도와 태그는 판정을 바꾸지 않는데 digest 에 들면
**오타 하나를 고치는 데도 문제 버전이 올라가고**, 버전 번호가 "무엇으로 채점됐는가"를 뜻하지
않게 된다. 경계는 한 문장이다 — **digest 에 드는 것은 판정을 바꾸는 것뿐이다.**

## catalog.yaml

```yaml
difficulty: MEDIUM        # INTRO EASY MEDIUM HARD EXPERT
tags:                     # content/tags.yaml 의 어휘만
  - array
  - two-pointers
competencies:             # 이 문제가 증거를 만들어 줄 수 있는 역량
  - ALGORITHM_CHOICE
  - CORRECTNESS
prerequisites:            # 먼저 풀어 두면 좋은 문제 (선택)
  - pair-sum-sorted
```

**난이도는 느낌이 아니라 무엇이 필요한가로 가른다.** 자료구조 하나를 한 번 순회하면
`INTRO`, 표준 패턴 하나를 그대로 쓰면 `EASY`, 패턴 둘을 조합하거나 관찰 하나가 필요하면
`MEDIUM`, 비자명한 관찰이나 증명이 필요하면 `HARD`, 그것을 여럿 엮어야 하면 `EXPERT` 다.
느낌으로 매기면 저작자마다 기준이 달라지고, 몇 달 뒤에는 같은 사람도 달라진다.

**역량은 "이 문제가 무엇을 가르치나"가 아니라 "이 문제를 푼 기록에서 무엇을 읽어낼 수
있나"다.** 모든 문제가 구현력의 증거를 만들지만, 복잡도 예측의 증거는 제한이 그것을
강제하는 문제에서만 나온다. 비워 둘 수 없다 — 비면 그 문제를 아무리 풀어도 숙련도가
움직이지 않는다.

태그를 늘리려면 `content/tags.yaml` 에 한 줄 더한다. 어휘 밖 값, 없는 선수 문제, 선수
관계의 순환은 검증 파이프라인의 `catalog` 단계가 막는다.

## hints.yaml

코칭 세션이 펼치는 도움 사다리다 (PRD FR-802). 역량마다 단계가 올라간다.

```yaml
MODELING:
  - "짝을 찾으려고 배열을 두 번 훑고 있다면, 안쪽 훑기가 무엇을 찾는지 말로 해 보세요."
  - "지나온 값을 값→인덱스로 기억해 두면 그 물음이 조회 한 번이 됩니다."
```

**어느 단계에서도 코드를 주지 않는다.** 코드를 주는 순간 그것은 도움이 아니라 정답이고,
그 뒤에 남는 증거는 아무것도 재지 못한다. 평문으로 쓴다 — 화면이 마크다운을 그리지 않아
별표가 그대로 보인다. 둘 다 테스트가 막는다 (`HintCoverageTest`).

**여기 없는 역량은 사다리가 저절로 만들어진다.** 복잡도는 `catalog.yaml` 의 목표 등급에서,
엣지케이스·정확성·반례는 `mutants/` 의 설명 줄에서 나온다. 같은 사실을 두 곳에 쓰지 않는
것이 규칙이라, 산문이 필요한 자리(모델링·구현력·문제 독해)에만 쓴다.

**오답의 설명 줄이 곧 힌트가 된다.** `// kind:` 다음 줄에 그 오답이 무엇을 잘못하는지
한 문장으로 적어 두면, 코칭이 그 **첫 문장**을 그대로 쓴다. 뒷문장은 오답의 구현을 설명하는
것이라 힌트로는 혼란스러우므로 첫 문장이 스스로 완결돼야 한다.

선언하지 않은 역량에 힌트를 쓰면 그 힌트는 영영 보이지 않는다 — 세션의 초점은 `catalog.yaml`
이 선언한 역량 중에서만 고르기 때문이다. 이것도 테스트가 막는다.

## 값 타입

`INT`, `INT_ARRAY`, `STRING`, `STRING_ARRAY`, `INT_MATRIX` 다섯 가지다. 연산자·괄호 같은
기호는 정수로 인코딩한다 — 인코딩 규칙을 본문에서 읽는 것도 문제의 일부다.

**문자열은 프로토콜 위에서 Base64 로 오간다.** 케이스 파일은 탭으로 필드를, 쉼표로 배열
원소를 나누는데 문자열에는 그 둘이 그냥 들어 있을 수 있다. 세 언어에서 똑같이 동작하는
이스케이프를 만드는 것보다 구분자가 없는 알파벳으로 옮기는 편이 틀릴 자리가 적고,
개행과 비ASCII 도 함께 해결된다. 문제를 쓰는 쪽에서는 신경 쓸 것이 없다 — 다만 **탭·쉼표·
비ASCII 가 든 경계 케이스를 하나씩 넣어 두면** 인코딩이 살아 있는지 계속 확인된다.

**격자는 `INT_MATRIX` 로 받는다.** 평탄화한 배열과 너비를 따로 받던 문제(`island-count`)가
남아 있지만, 새 문제는 그러지 않는다 — 너비를 인자로 받으면 "행 길이가 모두 같다"는 약속을
지킬 자리가 없다. 격자 문제에는 **직사각형과 빈 격자 케이스를 넣어 둔다.** 정사각형만 두면
행과 열을 맞바꾼 구현이 그대로 통과한다.

콘텐츠 검증(§6.3)은 코틀린 참조 구현만 돌린다. 자바·파이썬 하네스가 값을 같은 형식으로
주고받는지는 `StringValueTest` 와 `MatrixValueTest` 가 따로 지킨다.

## 오답을 고르는 기준

`mutants` 는 **그 알고리즘에서 실제로 자주 나는 실수**만 담는다. 아무 코드나 망가뜨리면
kill rate 는 쉽게 100% 가 되지만, 그 숫자는 테스트가 좋다는 뜻이 아니라 오답이
엉성하다는 뜻이다.

오답이 살아남으면 둘 중 하나다. **테스트가 약하거나, 오답이 사실은 정답이거나.** 후자를
먼저 의심한다 — 정렬된 두 수 합의 `left <= right` 는 "정답이 항상 존재한다"는 조건 때문에
도달할 수 없었고, 홀로 남은 수의 "합 차이" 방식은 Int 가 넘쳐도 2^32 나머지 안에서
답이 맞았다.

## 성능 케이스를 잡는 법

느린 풀이가 무너지는 지점은 배열 길이가 아니라 **연산 수**다.

- `O(n*k)` 는 `k` 를 키워야 갈린다. `n` 만 키우면 `k` 가 작아 통과한다.
- 두 겹 루프의 비용은 답과 무관하다. 답이 `Int` 를 넘지 않아야 한다면, 정렬된 큰 배열을
  써서 답은 작게 두고 비교만 `n^2/2` 번 일어나게 한다.
- 유니온 파인드는 합치는 방향에 따라 깊어지는 쪽이 다르다. 두 순서를 모두 넣어야
  반대로 구현한 풀이가 우연히 통과하지 않는다.

**성능 오답은 자릿수로 져야 한다.** 배로 지면 안 된다 — 시간 초과로 잡는 오답이라
판정이 머신 속도에 달리고, 빠른 머신에서는 통과해 버린다. 실제로 `gcd-of-array` 의
"가장 작은 값부터 나눠 보기"가 그랬다. 20억 번을 헛도는데 그 20억 번이 2초 한도와
같은 자릿수라, **한가한 머신에서는 통과하고 바쁜 머신에서는 잡혔다.** 공개 게이트가
머신 속도에 좌우된다는 뜻이다 (§12.1 재현성).

연산 수를 못 늘리겠으면 — 예컨대 바깥 루프가 이미 `Int` 상한에 걸렸으면 — 케이스를
키우는 대신 **오답을 바꾼다.** 같은 문제에서 뺄셈식 유클리드는 값에 비례하므로
`gcd(1, 20억)` 하나에 20억 번을 빼고, 그것을 원소마다 한다. 자릿수가 다르면 어떤
머신에서도 결과가 같다.

`validateContent` 의 `performance-margin` 단계가 이 여유를 재고, **3배를 못 넘기면
공개를 막는다.** 시간으로만 잡힌 오답을 한도의 3배로 한 번 더 돌려 실제 시간을 본다.

```
✗ performance-margin: 한도를 겨우 넘는 오답: quadratic--scans-forward(1.1배)
```

- **값으로도 잡히는 오답은 재지 않는다.** 그 판정은 머신과 무관하다.
- **메모리로 잡히는 오답도 본다.** 다만 배수가 아니라 "3배로 늘려도 여전히 넘치는가"만
  묻는다 — 메모리로 죽은 실행은 사용량을 남기지 않고, 남기는 값도 정점이 아니라 케이스가
  끝난 시점의 힙이다. 자원 하나만 확실하면 되므로, 시간으로 넉넉히 지면 메모리는 재지 않는다.
- **케이스마다 넉넉할 필요는 없다.** 작은 입력에서 아슬아슬한 것은 부분 점수 그룹의
  의도다. 어디선가 확실히 잡히면 되므로, 시간으로 걸린 **모든 그룹의 모든 케이스**를
  뒤에서부터 재서 가장 크게 이긴 값을 쓴다.
- **1배 아래로 나오면** 다시 돌렸을 때 한도 안에 끝났다는 뜻이다. 그 오답은 사실상
  잡히지 않고 있다.

여유를 못 벌릴 때가 있다. 오답의 비용이 자료형 상한에 걸리는 경우다 — `power-mod` 의
`linear-multiply` 는 지수만큼 곱하는데 지수가 `Int` 를 넘을 수 없다. 그때는 케이스 대신
**성능 그룹의 시계를 조인다**: `perf_groups(time_multiplier=0.5)`. 정답 풀이는 한도의
1% 도 안 쓰므로 조여도 영향이 없다.

## 걸리는 것들

| 증상 | 원인 |
|---|---|
| 기대 출력이 Int 범위를 넘는다 | 도구가 생성 시점에 막는다. 입력을 줄이거나 제약을 바꾼다 |
| 출력 한도를 넘는다 | 배열을 돌려주는 문제는 원소 수가 곧 출력 크기다. `limits.outputBytes` 를 올린다 |
| 성능 오답이 살아남는다 | 연산 수가 모자란다. 한가한 머신에서 다시 돌려 본다 — 바쁠 때만 잡히면 자릿수가 모자란 것이다 |
| 케이스를 고쳤는데 등록이 거부된다 | 공개된 버전은 불변이다. `Problem(version=...)` 을 올린다 (§6.1) |
| 케이스를 지웠는데 남아 있다 | 도구는 파일을 덮어쓸 뿐 지우지 않는다. 이름을 바꿨으면 옛 파일을 지운다 |
| 고친 적 없는 문제가 공개 409 | 검증 파이프라인이 바뀌어 보고서가 무효다. docs/running-locally.md 를 본다 |

## 오답이 살아남을 때

검증이 "살아남은 오답"을 내면 원인은 셋 중 하나다.

- **테스트가 약하다.** 그 오답이 틀리는 입력을 케이스에 더한다. 대개 이것이다.
- **동치 변이다.** 무작위 입력 수십만 개로 정답과 견줘도 갈리지 않으면 그 오답은 오답이
  아니다. 걷어내고 진짜 실수로 바꾼다 — 회의실 문제의 "방을 하나만 돌려받는" 변이가 그랬다.
- **너무 빨라서다.** 성능 오답인데 JIT 가 안쪽 반복을 벡터화해 한도 안에 끝나는 경우다.
  10^10 번의 단순한 max 비교는 2초가 안 걸린다. 그때는 입력을 키우거나(출력 한도에 걸리면
  `perf_groups(time_multiplier=)` 로 시간을 조인다), 오답을 **가장 흔한 첫 풀이의 실제
  모양**으로 바꾼다 — 창마다 부분 배열을 복사하는 풀이는 할당 때문에 숨을 데가 없다.

tie-break 같은 순서 규칙의 누락은 **작은 양수로만 시험하면 안 잡힌다.** 해시맵이 우연히
오름차순이다. 해시 순서가 어긋나는 값(100, 3, 17)으로 케이스를 잡는다.
